# Implementation plan: FocusFlow 1.3.0 progress and carry-over

**Spec:** `docs/superpowers/specs/2026-10-02-focusflow-1.3.0-progress-carry-over-design.md`  
**Parent spec:** `docs/superpowers/specs/2026-09-07-focusflow-1.2.0-scheduled-day-design.md`  
**ADRs:** `docs/adr/0026-checkpointed-remaining-effort.md`, `docs/adr/0027-revision-preserving-replan.md`  
**Glossary:** `CONTEXT.md`  
**Created:** 2026-10-03  
**Goal scope:** One milestone: a Task's remaining effort, recorded work, generation from that effort, and revision-preserving re-planning of the same Daily plan.

## Summary

Ship milestone 1.3.0 so a Task carries remaining effort separately from time spent and from its whole-task estimate. Users record done, partly done, or skipped outcomes, plus dated unplanned work. An explicit reassessment is a checkpoint. Later-day generation places current remaining effort through the unchanged 1.2.0 scheduler. A plan with any work outcome cannot be regenerated or deleted; re-planning the current day appends a schedule revision to the same Daily plan. The dashboard and plan detail compare planned duration with known actual duration and can inspect earlier revisions.

Out of scope: pace or future-deadline forecasts, task dependencies, recurring tasks, subtasks, calendar sync, the multi-day Gantt, live timers, actual start and end times, drag-to-reschedule, manual block editing, and peak-aware placement. Do not change authentication, CSRF, Flyway's baseline policy, or the placement algorithm. Do not invent cadence or fixed-break history for a migrated 1.2.0 plan.

This is one milestone, not separate product specs. Remaining effort is the quantity the scheduler places; carry-over is that quantity on a later generation; re-planning is another revision of the same plan after outcomes exist. None of those slices is a user-visible product without the others, and they share the Task and Daily plan aggregates. The slices below exist so each step stays testable and so later steps do not edit the migration, persister, and day view at the same time.

## Discovery notes

- Reuse: `DailyPlanScheduler` and the pure `com.focusflow.schedule` planners; `SchedulePostconditionValidator` conservation (the ranked quantity is already what gets checked); `OwnerSchedulingLock` inside the short persist transaction only; `ConflictException` / `BadRequestException` codes; task snapshots that already survive source deletion via `source_task_id` and `ON DELETE SET NULL`; `GeneratePlanCard` conflict refetch; `DayTimeline` and `DailyPlanView`; session-local `regeneratePrompt`; Vitest beside components; ArchUnit rules that keep `schedule` off Spring, JPA, and `plan.dto`.
- Constraints: Java 21, Spring Boot 3.4, PostgreSQL, Hibernate `ddl-auto: validate`. The next migration is `V5` after `V4__scheduled_day_block_constraints.sql`. Repositories must not depend on `..dto..`. Provider calls stay outside the owner lock. The client supplies the current date and re-plan cutoff. First-party API: backend slices can land before the frontend on this branch. `OpenApiSnapshotTest` stays out of intermediate verification and is refreshed once in T11.
- Patterns to follow: one package per feature, controller delegates to service, service owns the transaction, cross-feature reads go through a facade. Pure policy gets its own package and records, as `schedule` did. Frontend features keep `api.ts`, `hooks.ts`, and tests beside the component.
- Anti-goals: do not rewrite `V1` through `V4`. Do not delete Daily plans in a migration. Do not subtract actual minutes from the whole-task estimate as the general rule. Do not infer omitted actual minutes. Do not auto-finish a Task. Do not auto-regenerate a stale plan. Do not hold the owner lock across an AI call. Do not draw actual minutes as clock intervals. Do not parallelize subtasks that edit `V5`, `DailyPlanPersister`, `DailyPlanService`, or `DailyPlanView`.

**Migration sequencing:** V5 is one non-destructive migration, but it cannot land as SQL alone. Hibernate validates the entity model, and today's persister inserts plan tasks and blocks directly on the plan. T1 therefore adds the revision, backfills one revision per existing plan, moves schedule metrics onto that revision, and teaches the current persister to write revision 1. Later slices add behavior. They do not add another migration unless a type-2 plan discovers a nullable column that must become non-null after its writer exists; that exception goes in this file's changelog before the migration is added.

**Metric ownership:** free minutes, scheduled work, required minutes, and both buffer figures live on the schedule revision. `DailyPlan` does not keep a second copy. The API still returns those figures at the top of the plan from the latest revision.

### T2 — Remaining-effort calculator

- [x] **Do:** Implement the pure ledger: done credits planned duration, partly done credits positive actual minutes, skipped credits zero, a checkpoint replaces the running value, earlier-dated work does not move it, and a same-save assessment is not also credited. Exhaustion without finish or a positive remainder fails closed. Unknown effort stays unknown. Correcting an event does not change its order.
- **Consumes:** none.
- **Produces:** `RemainingEffortCalculator.apply(Integer startingRemaining, List<EffortEvent> events) -> EffortAssessment`. Events are `EffortEvent.WorkCredit(workDate, firstRecordedAt, saveId, outcome, plannedMinutes, actualMinutes)` and `EffortEvent.Checkpoint(workDate, firstRecordedAt, saveId, assessedRemainingMinutes)`. Outcomes are `WorkOutcome.DONE`, `PARTLY_DONE`, and `SKIPPED`. `AcceptedEffort.remainingMinutes()` is the assessed remainder, and null stays unknown. Callers reject a non-accepted exhaustion; they do not reimplement credit.
- **Acceptance:** Done with a known remainder subtracts the block's planned minutes, including when actual minutes are a smaller positive number or are omitted. Partly done subtracts the entered positive actual minutes. Skipped subtracts nothing. A checkpoint replaces the value so far, and only later-ordered events credit further. Events order by work date, then by `firstRecordedAt`; a correction keeps that position. A checkpoint and a credit that share a save do not both apply. Unknown starting effort stays unknown through credits until a checkpoint sets it. Exhaustion to zero or below, without a finish or a positive checkpoint in that assessment, is rejected and leaves the prior value unchanged.
- **Compatibility:** `com.focusflow.schedule` placement rules are unchanged. `effort` does not depend on Spring, JPA, or `plan.dto`.
- **Blocked by:** —
- **Plan mode:** high
- **TDD suitable:** yes
- **Verification:** `cd backend; .\gradlew.bat test --tests "*RemainingEffortCalculatorTest" --tests "*LayeredArchitectureTest"`

### T3 — Task finish, cancel, reopen, and reassessment

- [x] **Do:** Wire the ledger into task commands. After progress exists, whole-task estimate edits do not change the remainder. Finish sets Done and zero. Cancel keeps the remainder and leaves the Task unplannable. Reopen requires a fresh positive or explicit unknown assessment. A stale effort version returns `PROGRESS_CONFLICT`. ## TDD note (Agent mode)

Per subtask, obey **`TDD suitable`**: **`yes`** means strict **test-driven-development** (red/green/refactor); **`partial`** applies it only to the testable slice; **`no`** means do not force test-first — still satisfy **Verification**. A behavior-preserving refactor with a covering suite is **`no`** (stay-green), not a new RED/GREEN pair. Type-2 planning → **planning-subtasks** skill. UI work is often **`partial`**: TDD the behavior core, verify polish and motion manually.

One subtask stays one subtask when it has many behaviors or a mixed test and manual slice. Behavior count is not a reason to split it. A type-2 plan orders those behaviors inside the same subtask.
