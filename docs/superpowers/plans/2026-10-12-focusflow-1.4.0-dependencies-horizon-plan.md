# Implementation plan: FocusFlow 1.4.0 dependencies and horizon

**Spec:** `docs/superpowers/specs/2026-10-11-focusflow-1.4.0-dependencies-horizon-design.md`  
**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`  
**Previous plan:** `docs/superpowers/plans/2026-10-02-focusflow-1.3.0-progress-carry-over-plan.md`  
**ADRs:** `docs/adr/0028-inherited-dependency-urgency.md` through `docs/adr/0035-horizon-snapshot-read.md`

**Created:** 2026-10-12  
**Goal scope:** One milestone: finish-to-start dependencies in daily planning, then a read-only seven-working-day horizon that reuses those rules.

## Summary

Ship milestone 1.4.0 so the owner can link tasks with finish-to-start dependencies, and so daily planning ranks and places work under those links. A blocker inherits urgency only through Open and In-progress tasks. Java repairs dependency order after the existing ranking validation. A dependent whose active blocker is not fully placed is unplaced as `BLOCKED`. The horizon then forecasts the next seven working days from live tasks, saved Daily plans, and assumed credit. It does not store a week plan or call the model.

Out of scope: persisted multi-day plans, a horizon start-date picker, historical reconstruction, AI ranking of forecast days, history-based pace, start-to-start or finish-to-finish links, lead and lag, subtasks, recurring tasks, drag-to-reschedule, manual block editing, a chart library, dependency arrows, refusing progress on a blocked task, expanding `needsRefresh` to dependency edits, and changes to cadence, minimum session, fixed breaks, commitments, trailing buffer, the hard window end, or peak-window display. Do not change authentication, CSRF, or Flyway's baseline policy.

This is one milestone, not separate product specs. Dependencies can be used before the horizon page exists, but the horizon is not a second product: it consumes the same dependency, repair, and `BLOCKED` rules. The slices below keep the migration, the pure packages, the planning pipeline, and the horizon page from being edited at the same time.

## Discovery notes

- Reuse: `TaskQueryService` as the plan feature's task read facade; `OwnerSchedulingLock` inside the short write; `ConflictException` and `BadRequestException` codes; `DailyPlanRankingValidator.validateOrder` for ids, duplicates, completeness, and block order; `WorkPlacementPlanner.place` and `SchedulePostconditionValidator`; `DailyPlanPersister.persistPlan` and `appendRevision`; `PlanReplanFreshness`; `ComposedDay` for today's saved rail; `TaskService.latestCheckpointOrder`; `UnplacedReason` stored as `VARCHAR(32)` with no check constraint; preference defaults in `SchedulingPreferenceDefaults`; Vitest beside components; ArchUnit rules that keep `schedule` and `effort` off Spring, JPA, and plan DTOs.
- Constraints: Java 21, Spring Boot, PostgreSQL, Hibernate `ddl-auto: validate`. The next migration is `V7` after `V6__done_task_zero_remaining.sql`. Plan services must not use task repositories. Provider calls stay outside the owner lock. The client supplies the horizon date and minute-aligned time. Frontend tests run with `npm run test:run`. `OpenApiSnapshotTest` stays out of intermediate verification and is refreshed once in T11.
- Patterns to follow: one package per pure policy, as `schedule` and `effort` did. Controllers delegate to services. Cross-feature reads go through a facade. Frontend features keep `api.ts`, `hooks.ts`, and tests beside the component. Shared response types live in `frontend/src/types/api.ts`.
- Anti-goals: do not rewrite `V1` through `V6`. Do not add `V8` for a column this plan already puts in `V7`. Do not delete tasks, plans, or preferences in the migration. Do not hold the owner lock across an AI call or a horizon read. Do not change the global React Query `staleTime`. Do not draw dependency arrows or add a chart library. Do not parallelize subtasks that edit `V7`, `DailyPlanService`, `DailyPlanPersister`, `DailyPlanScheduler`, or `TaskList`.

**Migration sequencing:** `V7` is the only migration. It adds nullable or defaulted columns and new tables; it does not move columns that current inserts already write. Current preference saves and plan generation keep working after the migration, before later slices map the new fields. Later slices add JPA mappings and behavior. They do not add another migration.

**Credit evidence:** equal remaining minutes do not identify an assessment. Each new daily-plan task stores `capturedCheckpointId` with no foreign key. Null means no checkpoint was captured, which is also the migrated state.

### T2 — Dependency cycle, inherited ranking, and repair

- [x] **Do:** Add the pure dependency package. Detect cycles through every link, assign urgency and inherited due dates through active chains only, and repair a block-ordered ranking without moving a later group ahead of an earlier one.

- **Consumes:** none. Inputs are records, not JPA entities.
- **Produces:** `DependencyLink`. `DependencyCycleCheck.wouldCycle` uses every link, including links through Done or Cancelled tasks. `InheritedRanking.assign` returns the inherited group, inherited due date, and "Needed for" task. A Done or Cancelled task stops that chain. Forecast-started ids passed in `forecastMustContinueIds` are must-continue and propagate through active chains. `DependencyOrderRepair.repair` keeps the earliest legal original index whose active blockers are already emitted. A repair that crosses groups fails as a broken invariant. `dependency` does not depend on Spring, JPA, or DTOs.
- **Acceptance:** A self-link and a duplicate are distinguishable by the caller, and a cycle through a Done task is a cycle. Open A with no due date does not inherit urgency from Open C when Done B sits between them. Open A that blocks Open B due today inherits B's due group, and "Needed for" names B. Ties prefer the earliest due date, then the lowest task id. Repair puts A before B inside that group and does not return a provider-style success when the only legal order would move a later group first. A task already listed as forecast-started makes its unfinished blocker must-continue.
- **Compatibility:** `com.focusflow.schedule` placement is unchanged in this subtask.
- **Blocked by:** —
- **Plan mode:** high
- **TDD suitable:** yes
- **Verification:** `cd backend; .\gradlew.bat test --tests "*DependencyCycleCheckTest" --tests "*InheritedRankingTest" --tests "*DependencyOrderRepairTest" --tests "*LayeredArchitectureTest"`



### T3 — Dependency link commands

- [x] **Do:** Let the owner add or remove one blocker of a task. Reject self-links, duplicates, and cycles, including a race that would store both halves of a cycle. Return both link directions on task reads, including finished tasks.

- **Consumes:** T1's `task_dependencies` table. T2's `DependencyCycleCheck.wouldCycle`.
- **Produces:** `POST /api/tasks/{id}/blockers` with `{ "blockerTaskId": number }` returns **200** `TaskResponse`. `DELETE /api/tasks/{id}/blockers/{blockerId}` returns **204**. `TaskResponse.blockedBy` and `blocks` are `TaskLinkResponse(taskId, title, status)` lists. Unknown or other-owner ids return **404**. Codes are `SELF_DEPENDENCY` **400**, `DEPENDENCY_EXISTS` **409**, and `DEPENDENCY_CYCLE` **409**. A missing delete is **404**. `TaskQueryService.findLinksByOwnerId` is the plan feature's read facade. Link edits do not change `effortVersion` or `needsRefresh`.
- **Acceptance:** Adding the same task returns `SELF_DEPENDENCY` and stores nothing. Adding the same pair twice returns `DEPENDENCY_EXISTS` on the second add. A cycle, including one through a Done task, returns `DEPENDENCY_CYCLE`. Two concurrent adds that would form a cycle produce one success and one `DEPENDENCY_CYCLE`. Deleting a task deletes every link in which it appears. List and get include finished links. A link edit leaves effort version and plan freshness unchanged.
- **Compatibility:** Create, update, finish, cancel, reopen, reassessment, and delete routes stay. The owner lock covers the cycle check and the insert or delete, not an AI call.
- **Blocked by:** T1, T2
- **Plan mode:** high
- **TDD suitable:** yes
- **Verification:** `cd backend; .\gradlew.bat test --tests "*TaskDependencyServiceTest" --tests "*TaskControllerTest" --tests "*TaskQueryServiceTest"`



### T4 — Leave blocked work unplaced

- [x] **Do:** When an active blocker in the same ranking is not fully placed, place none of the dependent task and record one `BLOCKED` row. Keep today's placement when no edges are supplied or every active blocker is fully placed.

- **Consumes:** none. The existing entry is `WorkPlacementPlanner.place(stage1, ranking, policy)`.
- **Produces:** `UnplacedReason.BLOCKED`. `TaskDependencyEdge`. `WorkPlacementPlanner.place(stage1, ranking, policy, edges)` and the existing three-argument method, which passes no edges. `SchedulePostconditionValidator` checks `BLOCKED` conservation and, when both tasks have sessions, that the dependent's first session starts at or after the blocker's last session ends.

## TDD note (Agent mode)

Per subtask, obey `TDD suitable`: `yes` means strict **test-driven-development** (red/green/refactor); `partial` applies it only to the testable slice; `no` means do not force test-first — still satisfy **Verification**. A behavior-preserving refactor with a covering suite is `no` (stay-green), not a new RED/GREEN pair. Type-2 planning → **planning-subtasks** skill. UI work is often `partial`: TDD the behavior core, verify polish and motion manually.

One subtask stays one subtask when it has many behaviors or a mixed test and manual slice. Behavior count is not a reason to split it. A type-2 plan orders those behaviors inside the same subtask.
