# Implementation plan: FocusFlow 1.2.0 the scheduled day

**Spec:** `docs/superpowers/specs/2026-09-07-focusflow-1.2.0-scheduled-day-design.md`  
**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`  
**ADRs:** `docs/adr/0002` through `docs/adr/0025`  
**Glossary:** `CONTEXT.md`  
**Created:** 2026-09-22  
**Subsystem scope:** The scheduled day (one product milestone: preferences, commitments, pure scheduler, plan cutover, and the day UI)

## Summary

Ship milestone 1.2.0 so a Daily plan is a minute-aligned clock schedule. Users keep in-code scheduling defaults until they save preferences. They can store dated commitments. Generation asks the model for a total ordering of at most 100 plannable tasks, then a two-stage Java scheduler places that order into the work window, reserves the latest free minutes as buffer, and snapshots each ranked task once. Scheduled blocks reference that snapshot. Regenerating a date compare-and-replaces the one plan for that owner and date and issues a new plan id. The dashboard and plan detail render a vertical time rail.

Out of scope: recorded actuals, carry-over, mid-day re-plan, peak-aware placement, timezones, overnight windows, calendar sync, recurring commitments or tasks, live timer, drag-to-reschedule, manual block editing, task dependencies, and the multi-day Gantt. Do not change authentication, CSRF, Flyway's baseline policy, or 1.1.0 observability except the bounded ranking-rejection reasons the spec adds.

This is one milestone, not separate product specs. Preferences and commitments exist to feed generation; the scheduler has no user-facing surface until generation persists it; the UI consumes that contract. Slices below match the spec's five steps, split only where a later slice would otherwise break the suite or share too many files to plan in one session.

## Discovery notes

- Reuse: owner-scoped services, `TaskQueryService` instead of plan-to-task repository access, `DailyPlanPersister` for the short transactional save, `ConflictException` → 409, `BadRequestException` → 400, `NotFoundException` → 404, `ApiErrorResponse` with `@JsonInclude(NON_NULL)`, cookie session plus CSRF, `PostgresIntegrationTest` Testcontainers, ArchUnit `LayeredArchitectureTest`, `apiRequest` 204 → `undefined`, React Query invalidation in `features/plans/hooks.ts`, confirm/toast/alert patterns from the UI spec.
- Constraints: Java 21, Spring Boot 3.4, PostgreSQL `time(0)` / `date`, Hibernate `ddl-auto: validate` after Flyway. Repositories must not depend on `..dto..`. `com.focusflow.schedule` must not depend on Spring, JPA, or `plan.dto`. First-party API: frontend and backend ship together, but backend slices can land first on this branch. `V1__baseline.sql` stays untouched.
- Patterns to follow: one package per feature (`plan`, `task`, `ai`), controller delegates to service, service owns the transaction boundary, cross-feature reads go through a facade. Frontend features live under `frontend/src/features/<feature>/` with `api.ts`, `hooks.ts`, and Vitest beside the component. New `/api/**` routes are already authenticated by `anyRequest().authenticated()`.
- Anti-goals: do not rewrite `V1`. Do not add a PostgreSQL exclusion constraint. Do not lock task CRUD. Do not infer "today" on the server. Do not keep `availableMinutes`, `/latest`, or a persisted warning bit. Do not copy task descriptions into plan snapshots. Do not invent a third placement rule for a short sliver. Do not parallelize subtasks that edit the same service, migration, or `DailyPlanView`.

**Migration sequencing:** the spec's end-state schema is one reshape. This plan lands it as two Flyway versions so each subtask can stay green. `V2` adds preferences, commitments, and the estimate constraint without touching plan rows. `V3` deletes pre-1.2.0 plans and replaces `daily_plan_items` in the same change as the generate rewrite. Concatenating them into one version would make preferences untestable until the plan aggregate is gone.
