# FocusFlow 1.2.0 Design — The Scheduled Day

Date: 2026-09-07

**Previous milestones:** `docs/superpowers/specs/2026-08-22-focusflow-1.0.2-design.md`, `docs/superpowers/specs/2026-08-26-focusflow-1.1.0-platform-hardening-design.md`

## Purpose

Through 1.0.2 a Daily plan is an ordered list of tasks plus a typed-in minute budget. 1.1.0 hardens the platform so the next product change can reshape that aggregate without losing the schema. This milestone is that change: a plan becomes a clock schedule.

The AI still produces a ranking. A new deterministic Java scheduler places that ranking onto a work window, inserts cadence and fixed breaks, honors commitments and a trailing buffer, and splits long tasks into sessions. The dashboard and plan detail render those blocks on a vertical time rail. Generating a plan for a date replaces any existing plan for that date.

This is a design document, not an implementation plan. It assumes 1.1.0 is already built: Flyway owns the schema, generate is non-transactional until a short persist step, `planDate` is required, and plan history is paginated summaries.

## Goals And Non-Goals

Goals:

- Persist per-user scheduling preferences (work window, focus cadence, minimum session length, trailing buffer, optional peak window, labelled fixed breaks) with in-code defaults so a user who has never opened settings can still generate a plan.
- Persist dated fixed-time commitments and plan around them as unavailable time.
- Replace `DailyPlanItem` with `DailyPlanTask` snapshots and `DailyPlanBlock` clock intervals. Expose scheduled blocks and unplaced work as separate response collections.
- Introduce a two-stage pure-Java scheduler: free intervals first, then placement with cadence splitting.
- Narrow the AI contract to a total ordering of every plannable task. The scheduler places ranked work until time is exhausted. `DailyPlanRankingValidator` checks ids, completeness, uniqueness, and block order only.
- Enforce one Daily plan per owner and planning date. Regenerating replaces it.
- Render the day as a vertical time rail on both the dashboard aside and plan detail, with peak hours shaded and unplaced work listed beside the rail.
- Report honest schedule metrics (`freeMinutes` and `scheduledWorkMinutes`) and derive the shortfall warning from plan entries rather than from a typed minute count or persisted warning bit.
- Preserve historical work through immutable task snapshots even when the source Task changes or is deleted.

Non-Goals:

- No recorded actuals, remaining-effort derivation, carry-over, or mid-day re-plan. Those are 1.3.0, which reuses this scheduler with a shrunk window.
- No peak-aware placement. The peak window is stored and shaded; ranking order still fills the day front to back.
- No user timezone preference. Times are wall-clock `LocalTime` / `LocalDate`.
- No sub-minute scheduling. All schedule times are minute-aligned.
- No overnight windows, overnight breaks, or overnight commitments.
- No calendar sync, recurring commitments, or recurring tasks.
- No live timer, drag-to-reschedule, or manual block editing.
- No change to authentication, CSRF, Flyway policy, OpenAPI freshness, or observability from 1.1.0, except new metrics tags if a bounded ranking-rejection reason is added.
- Nothing from 1.4.0: task dependencies and the multi-day Gantt.

## Domain Language

Terms below amend `CONTEXT.md`. Prefer the glossary when they disagree with older specs.

**Work window**: The inclusive-start exclusive-end wall-clock span of one planning day (for example 09:00–18:00).
_Avoid:_ Available minutes, day length

**Focus cadence**: An optional target focus stretch plus a cadence-break length. The scheduler uses look-ahead to split work near the target without creating fragments shorter than the minimum session.
_Avoid:_ Pomodoro (unless the user has configured 25/5)

**Minimum session**: The shortest work block the scheduler will emit as its own session, except when a leftover fragment is all that remains of a task and nothing earlier can absorb it.

**Fixed break**: A labelled recurring daily unavailable window stored on scheduling preferences (for example lunch 12:00–13:00).

**Commitment**: A labelled one-off unavailable window on a specific calendar date (for example a meeting). Not a Task.

**Trailing buffer**: The last N minutes of the work window reserved as contingency and rendered as a distinct block. Not available for placement.

**Peak window**: An optional wall-clock span shaded on the timeline. It does not change placement.

**Daily plan task**: One ranked snapshot of a plannable Task inside a Daily plan. It owns task-level snapshot data and any unplaced remainder.

**Daily plan block**: One minute-aligned clock interval inside a Daily plan. A work block references a Daily plan task; rest, commitment, and buffer blocks do not.

**Scheduled block**: The response representation of a placed Daily plan block.

**Work session**: A scheduled work block for one Task snapshot. Several sessions of the same Task may exist in one plan. Session labels (`2 of 3`) are derived by grouping on immutable source-task identity.

**Unplaced work**: The response representation of a Daily plan task that is not on the clock, or has an unplaced remainder, with reason `NO_ESTIMATE` or `OUT_OF_TIME`.

**Free minutes**: The total minutes of free intervals after subtracting fixed breaks, commitments overlapping the window, and the trailing buffer. Cadence breaks consume some of this time during placement.

**Scheduled work minutes**: The sum of durations of scheduled work blocks after cadence breaks and interval boundaries have been applied.

**Required minutes**: The sum of known estimates on must-include candidates at generate time.

**Task snapshot**: Immutable source-task identity, title, priority, status, due date, and estimate copied onto a Daily plan task at generation time, with an optional live reference to the source Task. Free-form description is not retained.

**Schedule snapshot**: The work window and peak window copied onto the Daily plan at generate time so later preference edits do not rewrite history.

**The plan for a date**: The single Daily plan for that owner and planning date. Generating again replaces it.
_Avoid:_ Latest plan for a date

## User Workflow

1. A user sets scheduling preferences, or skips that and keeps the in-code defaults.
2. Optionally they add commitments on the planning date.
3. They generate a plan for an explicit planning date. If a plan already exists for that date, they confirm replacement.
4. The backend loads plannable tasks and commitments, asks the model for a total ranking, validates ordering, runs the scheduler, replaces any existing plan for that date, and returns the timed plan.
5. The dashboard and plan detail show a vertical rail spanning the snapshot window: work sessions, cadence breaks, fixed breaks, commitments, and buffer, with peak hours shaded. Unplaced work sits in a companion list with a reason.
6. If must-include work is unplaced, a shortfall warning lists those tasks.

## Architecture

No change to the layered model. Controllers still delegate to services; services own transactions; repositories persist; cross-feature reads go through facades. Three additions:

- `com.focusflow.preferences` — preferences aggregate, defaults, and HTTP API.
- `com.focusflow.commitment` — dated commitments and HTTP API.
- `com.focusflow.schedule` — the two-stage scheduler as pure functions over immutable records. It must not depend on Spring, JPA, or `plan.dto`. `DailyPlanService` maps entities into scheduler input and scheduler output into entities.

Plan generation keeps 1.1.0's two boundaries. Non-transactional orchestration loads a generation snapshot (tasks, effective preferences, commitments for the date), checks the replace precondition before spending a provider call, calls the provider, validates ranking, and runs the scheduler. A short transactional persist step locks the owner row, rechecks the replace precondition, reloads task references, and replaces or creates the plan. A candidate Task deleted in that window returns coded **409** and saves nothing; ordinary edits do not alter the captured snapshot.

The owner row is the serialization boundary for all scheduling mutations: plan create/replace/delete, commitment create/update/delete, and scheduling-preferences `PUT`. Each operation locks that row before checking its scheduling invariant. Task CRUD deliberately remains outside this lock: generation owns a task snapshot and detects deletion while persisting it.

`LayeredArchitectureTest` gains the same DTO rule for any new repositories. Preferences and commitment response types stay in their `dto` packages; repositories return entities or package-local projections.

## Schema

The next Flyway version after 1.1.0's `V1` is forward-only and destructive for plans. It needs the same backup-first README procedure 1.1.0 established for legacy adoption. Tasks, users, preferences, and commitments are not deleted.

### Destructive plan reset

1. Delete all rows in `daily_plan_items`, then `daily_plans`.
2. Drop `daily_plans.available_minutes` and `daily_plans.warning`.
3. Drop `daily_plan_items` and create `daily_plan_tasks` and `daily_plan_blocks`.
4. Add a unique constraint on `daily_plans (owner_id, plan_date)`.
5. Convert every legacy `tasks.estimated_minutes <= 0` value to null, then add a database constraint requiring an estimate to be null or positive.

After this migration every Daily plan in the database has clock times, so the frontend has one rendering path.

One row per scheduled clock interval.

| Column | Type | Notes |
|---|---|---|
| `id` | `bigint` identity | Primary key |
| `daily_plan_id` | `bigint` not null | Foreign key to `daily_plans` |
| `daily_plan_task_id` | `bigint` null | Required for `WORK`; null otherwise |

| `start_time` | `time(0)` not null | Block start |

Invariant, enforced in the service before persist and by check constraints where PostgreSQL can express it: every block has a positive start/end interval; `WORK` blocks have a plan-task reference and no label; non-work blocks have a label and no plan-task reference. Each work block's task belongs to the same daily plan. Cross-row ordering and non-overlap remain scheduler postconditions.

The API exposes blocks in chronological order and plan tasks with a non-null unplaced reason in ranking order.

### New tables

**`scheduling_preferences`** — at most one row per user (`owner_id` unique). Columns: `work_day_start`, `work_day_end`, `cadence_enabled`, `target_focus_minutes`, `break_minutes`, `min_session_minutes`, `buffer_minutes`, nullable `peak_start` / `peak_end`. Absence of a row means in-code defaults apply; generating does not insert a row.

**`fixed_breaks`** — children of `scheduling_preferences`: `label`, `start_time`, `end_time`. Overlapping fixed breaks are rejected on write.

**`commitments`** — owner-scoped: `title`, `commitment_date`, `start_time`, `end_time`. Overlapping commitments for the same owner and date are rejected on write.

All new time columns are PostgreSQL `time(0)` without time zone, matching minute-aligned `LocalTime`. Dates are `date`, matching `LocalDate`. Request validation rejects non-zero seconds or nanoseconds instead of truncating them.

Task create and update now require `estimatedMinutes` to be null or positive. Individual estimates remain PostgreSQL / Java integers; totals such as `requiredMinutes` use `bigint` / `long` so a large candidate set cannot overflow.

## Scheduling Preferences

### In-code defaults

Used whenever the owner has no preferences row:

| Field | Default |
|---|---|
| Work window | 09:00–18:00 |
| Cadence enabled | yes |
| Target focus | 50 minutes |
| Cadence break | 10 minutes |
| Minimum session | 15 minutes |
| Trailing buffer | 0 minutes |
| Peak window | none |
| Fixed breaks | none |

`GET` always returns these effective values. A boolean `persisted` tells the settings page whether the user has saved.

### Validation on save

- `workDayEnd` is after `workDayStart`. No overnight window.
- Every supplied time is minute-aligned.
- When cadence is enabled, `targetFocusMinutes >= minSessionMinutes >= 1` and `breakMinutes >= 1`.
- When cadence is disabled, target and break values are retained for a later re-enable but ignored by scheduling.
- `bufferMinutes >= 0` and strictly less than the window length in minutes.
- Peak window, if present: start before end, and both lie inside the work window.
- Each fixed break: non-blank label of at most 255 characters, start before end, wholly inside the work window, no overnight, no overlap with another fixed break.

Saving replaces the aggregate, including the full fixed-break list, while holding the owner scheduling lock.

## Commitments

A commitment is not a Task and does not appear in the ranking. The scheduler treats its interval as unavailable, clipped to the work window, and emits a `COMMITMENT` block for the clipped span when the interval overlaps the window. A commitment wholly outside the window is stored but does not affect the plan.

Validation on write: non-blank title of at most 255 characters, minute-aligned start before end, no overnight, no overlap with another commitment of the same owner on the same date. `PUT` may replace title, date, start, and end; moving a commitment validates overlap on the destination date.

## The Two-Stage Scheduler

Both stages are pure functions. Tests construct records and assert records. No Spring context.

### Stage 1 — free intervals

Input: work window, fixed breaks, commitments for the planning date, trailing buffer minutes.

1. Start with `[workDayStart, workDayEnd)`.
2. Clip fixed breaks and commitments to that window and subtract their union exactly once.
3. Normalize fixed-break and commitment overlaps into non-overlapping scheduled segments. `COMMITMENT` wins over `FIXED_BREAK`; lower-precedence intervals remain visible only in portions not covered by higher precedence. Example: lunch 12:00–13:00 plus a meeting 12:30–13:30 becomes lunch 12:00–12:30 and meeting 12:30–13:30.
4. From the resulting free intervals, reserve the latest `bufferMinutes` of **free** time as `BUFFER`. Buffer may split around unavailable time. If fewer free minutes exist than requested, reserve all of them; snapshot both the requested and realized values.
5. Return ordered work-free intervals and normalized unavailable segments. Each boundary records whether it is restorative: fixed breaks reset cadence; commitments do not.

`freeMinutes` is the sum of work-free interval durations after buffer reservation. `realizedBufferMinutes` is the total duration of the buffer blocks; it equals the requested amount unless fixed breaks and commitments leave too little free time.

Idle gaps that later arise because a cadence break does not fit in a leftover sliver are not computed here.

### Stage 2 — placement

Input: free intervals and boundary metadata from stage 1, ranking (total order of `DailyPlanTask` candidates with must-include flags), `cadenceEnabled`, `targetFocusMinutes`, `breakMinutes`, and `minSessionMinutes`.

Walk the ranking. Optional work may be partially placed: ranking outranks packing efficiency, so a shorter lower-ranked task never jumps ahead merely because it would finish. Maintain a cursor in the free intervals and a `focusClock` of focused work since the last restorative break. Commitments pause the cursor but preserve the focus clock; fixed and cadence breaks reset it.

For each task:

- **No estimate.** Emit one unplaced `WORK` item, reason `NO_ESTIMATE`. Consume no time.
- **Has estimate.** Place `remaining = estimate` as follows, then if `remaining > 0` emit one unplaced `WORK` item, reason `OUT_OF_TIME`, `unplacedMinutes = remaining`. A task may therefore have placed sessions and an unplaced remainder.

Placement loop while `remaining > 0` and free time remains:

1. Advance across exhausted intervals. A crossed fixed break resets `focusClock`; a crossed commitment preserves it.
2. The minimum-session rule applies whether cadence is enabled or disabled. If cadence is disabled, place up to the task remainder or current free-interval remainder without adding cadence breaks.
3. When cadence is enabled, before starting a new work session, if the remaining focus budget (`targetFocusMinutes - focusClock`) is below `minSessionMinutes`, take an early cadence break when it fits. If it does not fit before the next boundary, leave that sliver idle and advance; a fixed break may reset cadence there, while a commitment does not.
4. When cadence is enabled, use look-ahead before emitting a work block or cadence break. Normally cap a session at the remaining focus budget. If that cap would leave a final task tail shorter than `minSessionMinutes`, absorb the tail into the current session when the current free interval has room. This may exceed `targetFocusMinutes` by at most `minSessionMinutes - 1`.
5. If an interval boundary would create a non-final session shorter than `minSessionMinutes`, leave the sliver idle unless it can extend the immediately preceding session of the same task without crossing a cadence break or unavailable boundary.
6. If the entire task remainder is shorter than `minSessionMinutes`, place it when it fits rather than leaving finishable work unplaced.
7. Emit the `WORK` block, advance the cursor, add its duration to `focusClock`, and subtract it from `remaining`.
8. When cadence is enabled, insert a cadence break only when positive estimated work remains to be placed. A trailing break after the last work session is not emitted.

After the ranking is exhausted, unused free time stays empty on the rail (no filler blocks). Emit the labelled unavailable and buffer blocks from stage 1.

Peak window is not an input to either stage.

### Postcondition validation

Before persistence, a separate pure validator checks the complete result:

- Scheduled blocks are minute-aligned, positive-duration, ordered, non-overlapping, and inside the work window.
- Normalized fixed-break, commitment, and buffer segments match stage 1 and are subtracted only once.
- For each positive-estimate daily plan task, scheduled work plus `OUT_OF_TIME` minutes equals its generation-time estimate.
- Each unestimated daily plan task has exactly one `NO_ESTIMATE` reason and no scheduled work.
- Every ranked daily plan task appears exactly once, and no unknown source-task identity appears.

Failure is an internal **500**, is logged with the request id, and saves nothing.

### Worked examples

Assume window 09:00–18:00, cadence 50/10, minimum session 15, lunch 12:00–13:00, buffer 0.

- **120-minute task at 09:00.** Sessions 09:00–09:50, 10:00–10:50, 11:00–11:20 with 10-minute cadence breaks between. Tail 20 ≥ 15, so it is its own session.
- **113-minute task.** Sessions 09:00–09:50 and 10:00–11:03. Look-ahead absorbs the 13-minute tail into the second session before emitting another break, so it exceeds the 50-minute target.
- **55-minute task.** One session 09:00–09:55. The 5-minute tail is absorbed into the first session.
- **New task after 40 focused minutes.** If at least 15 minutes of the new task remain, the 10-minute focus budget is too short to start it; take an early cadence break, then start a valid session.
- **Must-include 8 hours of estimates, 7 free hours.** Place in ranking order until free intervals are gone; remaining must-include estimates become `OUT_OF_TIME` unplaced items. The rail never extends past 18:00.
- **Unestimated must-include.** Companion list, reason `NO_ESTIMATE`; warning fires.
- **Fully unavailable day.** Still call the provider to establish ranking, persist unavailable blocks, and emit every task as unplaced. Required work creates a warning.

## AI Ranking And Validation

The provider returns one authoritative order: `{ "taskIds": [7, 2, 9] }`. Array order is ranking order; the AI does not return positions.

- List every plannable task, including status, as today.
- Instruct the model to return **every** listed id exactly once, in block order (must-continue, then due/overdue, then optional), using the existing intra-block ranking guidance.
- Do not mention leftover minutes, optional-fit arithmetic, or clock times. Placement is not the model's job.
- `AiDailyPlanRequest` drops `availableMinutes`. The prompt may still mention the planning date.
- One generation accepts at most 100 plannable candidates. Above that, return **400** with code `PLAN_CANDIDATE_LIMIT` before the provider call. Prompt formatting truncates each description to 500 characters without modifying persisted Task data.

`DailyPlanRankingValidator` rejects when:

- A task id is not in the candidate set.
- Any candidate is missing.
- Any candidate appears more than once.
- Walking ordered task ids, a later block appears before an earlier block.

It no longer computes leftover or optional overflow. Intra-block mis-order is still accepted. Rejection still surfaces as **502** and saves nothing. Ranking-rejection metrics keep a bounded reason enum; add `DUPLICATE_TASK` and `MISSING_OPTIONAL` (missing must-include reasons stay). Java assigns positions only after scheduling.

## Generation Flow

1. Require `planDate`; accept optional `replacePlanId` as a concurrency precondition, not a scheduling input.
2. Load the current plan for the owner/date and check the precondition before the provider call: no current plan plus no id may create; current plan plus no id returns **409** `PLAN_EXISTS`; a matching id may replace; every other combination returns **409** `PLAN_CHANGED`.
3. Load plannable tasks. Empty set → **400** `no plannable tasks available for planning`, no provider call. More than 100 → **400** `PLAN_CANDIDATE_LIMIT`, no provider call.
4. Validate every non-null estimate as positive; Task create/update enforce the same rule. Load effective preferences and commitments for `planDate`.
5. Classify candidates into blocks 1 / 2 / 3 as in 1.0.2. Compute `requiredMinutes` with `long`.
6. Call the provider with the full candidate list. Validate ranking.
7. Run stage 1, stage 2, then postcondition validation. A zero-free-time day follows the same flow.
8. In one short transaction, lock the owner row and recheck the replace precondition. Reload live task references, build one `DailyPlanTask` snapshot per candidate, then create or replace the plan; concurrent state change returns coded **409** and the transaction saves nothing.
9. Persist the window/peak snapshot, `freeMinutes`, `scheduledWorkMinutes`, `requiredMinutes`, requested/realized buffer minutes, daily plan tasks, and scheduled blocks. Return plan detail.

`createdAt` on replace is the new generation time.

## Shortfall Warning

No persisted warning JSON or `hasWarning` bit. The mapper builds `warning` as null unless at least one Daily plan task has `mustInclude == true` and a non-null unplaced reason.

When non-null:

- `requiredMinutes`, `freeMinutes`, and `scheduledWorkMinutes` from the plan snapshot.
- `outOfTimeTasks` — must-include Daily plan tasks with reason `OUT_OF_TIME`: `sourceTaskId`, `title`, `unplacedMinutes`.
- `unestimatedTasks` — must-include Daily plan tasks with reason `NO_ESTIMATE`: `sourceTaskId`, `title`.

Optional unplaced work does not create a warning. The history summary query derives `hasWarning` with an existence predicate over must-include Daily plan tasks with an unplaced reason.

## API Shape

First-party product API; frontend and backend change atomically. OpenAPI snapshot updates with the implementation.

### Plans

**`POST /api/daily-plans/generate`** — body `{ "planDate": "YYYY-MM-DD", "replacePlanId": null }`. `replacePlanId` is optional and follows the compare-and-replace matrix above. Obsolete `availableMinutes` is ignored under the existing unknown-property policy; it is absent from OpenAPI and the first-party frontend. Success remains **201** with the extended `DailyPlanResponse` because each generation creates a new plan identity even when it atomically removes the previous plan for that date.

**`GET /api/daily-plans/by-date?planDate=`** — replaces `/latest`. Returns the one plan for that date, or **204**.

**`GET /api/daily-plans`**, **`GET /api/daily-plans/{id}`**, **`DELETE /api/daily-plans/{id}`** — unchanged paths. Summary drops `availableMinutes` and generic item count. Delete takes the owner scheduling lock.

Extended `DailyPlanResponse`: `id`, `planDate`, `createdAt`, `windowStart`, `windowEnd`, `peakStart`, `peakEnd`, `freeMinutes`, `scheduledWorkMinutes`, `requiredMinutes`, `requestedBufferMinutes`, `realizedBufferMinutes`, `warning`, `blocks`, `unplacedWork`.

`blocks` is a discriminated collection:

- `WORK`: `kind`, `startTime`, `endTime`, `sessionIndex`, `sessionCount`, and `taskSnapshot`.
- `CADENCE_BREAK`, `FIXED_BREAK`, `COMMITMENT`, `BUFFER`: `kind`, `startTime`, `endTime`, `label`.

`unplacedWork`: `reason`, nullable `unplacedMinutes`, and `taskSnapshot`.

`taskSnapshot`: immutable `sourceTaskId`, nullable `taskReferenceId`, title, priority, status, due date, estimate at generation, and `mustInclude`. `taskReferenceId` is null after source deletion. Description is deliberately absent.

`sessionIndex` / `sessionCount` are 1-based and derived by grouping scheduled work on a `DailyPlanTask`. Unplaced remainders are not counted as sessions.

`DailyPlanSummaryResponse`: `id`, `planDate`, `createdAt`, `scheduledWorkMinutes`, `workSessionCount`, `scheduledTaskCount`, `unplacedWorkCount`, `hasWarning`.

### Preferences

- `GET /api/scheduling-preferences` — **200** with effective values and `persisted`.
- `PUT /api/scheduling-preferences` — owner-locked upsert; **200** with persisted values (`persisted: true`).

### Commitments

- `GET /api/commitments?from=&to=` — owner-scoped, inclusive date range, required query params, **400** if missing or `from > to`.
- `POST /api/commitments` — create under the owner scheduling lock.
- `PUT /api/commitments/{id}` — replace title, date, and window under the owner scheduling lock. Moving dates validates destination overlap and invalidates old- and new-date queries. Missing or other-user **404**.
- `DELETE /api/commitments/{id}` — delete under the owner scheduling lock; **204**. Missing or other-user **404**.

CSRF follows other state-changing requests.

## Error Handling

Existing codes stay. Additions:

- **400** — invalid preferences or commitments (overlap, overnight, precision, bounds); non-positive task estimate; commitment list range; `PLAN_CANDIDATE_LIMIT`.
- **409** — `PLAN_EXISTS`, `PLAN_CHANGED`, or `TASK_MISSING_DURING_GENERATION`.

`ApiErrorResponse` gains nullable `code`. Codes are bounded stable identifiers; clients never branch on human-readable `message`. Existing errors may leave `code` null.

## Frontend

Follow the UI spec's confirmation, toast, alert, and query-invalidation patterns.

### Settings (`/settings`)

New authenticated route. Sidebar gains a Settings link. The page edits work window, cadence, minimum session, trailing buffer, optional peak window, and the list of fixed breaks. Saving `PUT`s the aggregate. Unsaved defaults render as the effective values with copy that they apply until saved.

### Commitments

On the dashboard planning column, a dated list for the selected planning date: add, edit (including moving date), and delete with the same confirm-on-delete pattern as tasks. This is the only commitment UI in 1.2.0.

### Generate

The dashboard gains a planning-date selector defaulting to browser-local today and synchronized to `?date=YYYY-MM-DD`. It drives `/by-date`, commitments, and generation; the task list remains unchanged.

`GeneratePlanCard` drops the available-minutes input. A create request omits `replacePlanId`. A `PLAN_EXISTS` or `PLAN_CHANGED` response first refetches `/by-date`; only then does the client present confirmation using the actual current plan id, or offer a fresh create if the date is now empty. Success toast; invalidate plan-by-date and history.

Plans remain immutable snapshots after generation. Relevant task, preference, or commitment edits never trigger provider calls or mutate saved plans. When the current client knows an affected plan exists, it shows a session-local “Regenerate to apply changes” prompt; 1.2.0 does not persist a stale flag.

### Day timeline

Replace the ordered list in `DailyPlanView` with a **vertical time rail** on both the dashboard aside and plan detail. Time runs top to bottom across the snapshot work window. Block height is proportional to duration. Cadence breaks, fixed breaks, commitments, and buffer use distinct border/fill patterns as well as colour (buffer is an outlined empty slice). The peak window, when present on the snapshot, is a shaded band. Hour labels sit in a gutter. Every block has an accessible label, is keyboard-focusable, and exposes kind, label, and time in a focus/hover tooltip or popover; short blocks remain proportional even when visible text does not fit.

Unplaced work renders in a companion list below the rail, with reason copy: "no estimate — add one to put it on the clock" or "out of time" plus unplaced minutes. Must-include unplaced items also appear in the shortfall alert above the rail. When `realizedBufferMinutes < requestedBufferMinutes`, a non-error note says that fixed breaks or commitments reduced contingency.

Empty state, loading skeleton, and error retry stay. A stale plan-detail URL that returns 404 directs users to `/dashboard?date=<planDate>` when its plan date is available from cached history state; otherwise it links to plan history. Plan history rows show scheduled minutes, work sessions, distinct scheduled tasks, unplaced work, and warning state; they do not grow a mini-rail.

## Testing Strategy

Existing style: JUnit 5 for the scheduler as plain unit tests, Mockito at service level, `@WebMvcTest` for HTTP and security, Testcontainers for persistence and the unique constraint, ArchUnit for the new packages, Vitest for the rail, settings form, generate confirm, and warning.

Highest-priority coverage:

- Stage 1: window minus lunch and commitment; overlaps normalize with commitment precedence and no double subtraction; buffer reserves the latest free minutes and reports requested versus realized capacity; commitment wholly outside the window is ignored; zero buffer is a no-op; fixed breaks must lie inside the window.
- Stage 2: look-ahead on the three splitting examples above; early break at a task boundary; commitments preserve cadence while fixed breaks reset it; disabled cadence still honours minimum session; cadence break that does not fit a sliver; unestimated tasks never occupy the clock; overflow stays inside the window and emits `OUT_OF_TIME`; partially placed optional work does not warn.
- Postconditions: reject overlap, out-of-window blocks, estimate-conservation failures, missing ranked tasks, and unknown source tasks before persistence.
- Ranking validator: missing optional id, duplicate id, block-order break, unknown id; leftover/optional-overflow cases from 1.0.2 no longer reject.
- Preferences GET without a row returns defaults (`persisted: false`); owner-locked PUT then GET round-trips; invalid precision, out-of-window and overlapping fixed breaks return 400.
- Commitments may move dates; owner-locked writes prevent concurrent overlaps; overlap returns 400; owner scoping returns 404.
- Generate compare-and-replace covers every precondition matrix branch before and after the provider call; owner locking preserves uniqueness under concurrent requests; deleted source Task returns coded 409; zero-free day succeeds; no plannable tasks and more than 100 candidates return coded 400 before the provider.
- Task create/update rejects zero and negative estimates; aggregate totals cannot overflow `long`.
- Migration: post-migrate plans are empty; legacy non-positive estimates become null; database positivity constraint and Hibernate `validate` pass.
- Daily plan task snapshot: editing or deleting a source Task does not rewrite or remove historical blocks; source snapshots retain title, priority, status, due date, and estimate but not descriptions; session grouping survives deletion.
- Frontend: rail patterns, keyboard labels and tooltips identify short blocks; companion list shows both reasons; planning date survives refresh in the URL; coded conflicts drive replacement; settings save sends the aggregate.

## Risks

**Destructive migration is irreversible without the backup.** Pre-1.2.0 plans are deleted. The README must say so in the same tone as 1.1.0's adoption procedure.

**1.1.0 must ship first.** This spec's schema is the next Flyway version, not a rewrite of `V1`.

**Absorb-vs-idle edge cases will dominate scheduler tests.** The rules above are the spec; an implementation that invents a third behaviour for a 14-minute sliver at lunch is a bug even if it "looks nicer."

**Replace deletes 1.3.0's future actuals.** 1.3.0 must tighten compare-and-replace to preserve or explicitly discard actuals. 1.2.0 only confirms because the plan is still disposable.

**Display-only peak hours can look like a broken preference.** Settings copy must say the band is visual until a later milestone.

## Learning Priorities

Consistent with the parent spec, weighted toward a testable domain function in Java: modelling minute-aligned `LocalTime` intervals, splitting a greedy placement algorithm into two stages so failures pin to one job, validating postconditions independently, narrowing an AI boundary to one ordered id array, and preserving immutable source snapshots while keeping optional live references.

## Suggested Decomposition

A type-1 plan derived from this spec should be marked **TDD suitable: partial**. The scheduler, ranking-validator narrowing, preference and commitment validation, replace-on-generate, and unique constraint are naturally test-first. The Flyway SQL, settings page layout, and rail CSS are not.

1. **Schema.** Destructive plan reset; unique constraint; `DailyPlanTask` / `DailyPlanBlock` tables; legacy estimate normalization and positivity check; Hibernate validate; README backup procedure.
2. **Preferences and commitments.** Defaults, cadence enablement, CRUD, minute precision/overlap validation, and owner-locked scheduling mutations. No generate change yet.
3. **Scheduler.** Stage-1 unavailable normalization plus latest-free-minutes buffer reservation, stage-2 look-ahead placement, and postcondition validation as pure unit tests.
4. **Generate rewrite.** Bounded ordered-id prompt, narrowed validator, plan-task snapshots, owner-locked compare-and-replace, derived metrics/warning, API/DTO/OpenAPI updates.
5. **Frontend.** Settings route, URL-backed planning date, commitments, refetched coded-conflict replacement flow, accessible vertical rail, warning and companion list.

Steps 3 and 4 are the product; 1 is the precondition; 2 can overlap 3; 5 consumes 4's contract.
