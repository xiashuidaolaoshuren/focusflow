# FocusFlow 1.3.0 Design — Progress and Carry-over

Date: 2026-10-02

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Previous milestone:** `docs/superpowers/specs/2026-09-07-focusflow-1.2.0-scheduled-day-design.md`
**Related UI spec:** `docs/superpowers/specs/2026-05-31-focusflow-frontend-ui-design.md`
**Domain glossary:** `CONTEXT.md`
**Roadmap:** `docs/superpowers/roadmap.md`

Decisions introduced here are recorded as [ADR 0026](../../adr/0026-checkpointed-remaining-effort.md) and [ADR 0027](../../adr/0027-revision-preserving-replan.md). The 1.2.0 decisions in ADRs `0002` through `0025` remain in force except where this document narrows them.

## Purpose

1.2.0 places each plannable Task's whole-task estimate onto one day's clock. It has no record of time spent, work completed, or effort still required, and regenerating a date deletes the previous plan.

1.3.0 adds that missing progress model without changing the placement algorithm. Actual minutes record time spent. Remaining effort estimates how long the Task still needs. Later-day generation carries unfinished Tasks forward by using that current remainder. Mid-day re-planning keeps the same Daily plan, preserves earlier schedule revisions, and schedules only what remains.

This is a design document, not an implementation plan. It assumes 1.2.0 is already built: one plan per owner and planning date, a two-stage scheduler, task snapshots, and compare-and-replace regeneration.

## Goals And Non-Goals

Goals:

- Record a work outcome of done, partly done, or skipped against a planned work block, with honest handling of missing actual minutes.
- Keep the whole-task estimate stable for comparison, and track remaining effort separately. An explicit reassessment is a checkpoint that earlier work does not override.
- Start a Task when worked progress is recorded, but require an explicit finish. Resolve an exhausted estimate in the same save.
- Record dated unplanned work without inventing a planned clock interval.
- Carry unfinished work into a later day's plan by considering the current plannable Tasks and their current remaining effort. Scheduled time alone grants no progress credit.
- Preserve effort snapshots and flag a plan whose assumptions are outdated. Refresh only through an explicit regeneration or re-plan.
- Refuse regeneration and deletion once a plan has any work outcome. Preserve historical actuals when a Task is deleted.
- Re-plan the remainder of the current day on the same Daily plan after elapsed work is reconciled. Retain every schedule revision, reload commitments, reuse the captured scheduling rules, and reset the focus calculation without claiming a break occurred.
- Show planned duration against known actual duration on the dashboard and plan detail. Inspect earlier revisions from plan detail.
- Reject a stale progress save or re-plan instead of overwriting newer state.
- Warn when due or overdue work does not fit the day being planned. Preserve existing Daily plans during upgrade, and allow re-planning only for plans that captured a complete scheduling snapshot.

Non-goals:

- No predictive warning that a future due date will be missed, and no pace-based forecast. That depends on a multi-day horizon and belongs to 1.4.0.
- No change to the 1.2.0 placement rules: cadence, minimum session, fixed breaks, commitments, trailing buffer, hard window end, or peak-window display.
- No task dependencies, recurring tasks, subtasks, calendar sync, or multi-day Gantt.
- No live timer, actual start and end times, drag-to-reschedule, or manual block editing.
- No inference of actual minutes from planned duration, and no clock position invented for a duration-only actual.
- No background plan generation and no duplicate carry-over Task.
- No destructive reset of existing Daily plans. A 1.2.0 plan remains usable for progress, but it cannot be re-planned until an untouched plan is regenerated under this milestone.
- No new authentication, CSRF, Flyway-policy, or observability design. New conflict responses use the existing coded-error contract.

## Domain Language

Terms below amend `CONTEXT.md`. Prefer the glossary when it disagrees with older specs.

**Whole-task estimate**:
The Task's estimate of its complete effort. It initializes Remaining effort and stays available for comparison.
_Avoid:_ Remaining effort, actual minutes

**Remaining effort**:
The current estimate of minutes still needed to finish a Task. It is unknown until an estimate or explicit assessment exists.
_Avoid:_ Actual minutes, whole-task estimate

**Actual minutes**:
Time spent on work. Unknown actual minutes are not zero and are not planned duration.
_Avoid:_ Planned duration, remaining effort

**Work outcome**:
The recorded result of a planned work block: done, partly done, or skipped.

**Remaining-effort checkpoint**:
An explicit reassessment of Remaining effort. Work dated before it can change history without changing that reassessment.

**Unplanned work**:
Time recorded against a Task on a date that has no corresponding planned work block.
_Avoid:_ Work session, scheduled block

**Schedule revision**:
One complete scheduling result retained by a Daily plan. The latest revision is actionable; earlier revisions are history.
_Avoid:_ Replacement plan

**Regeneration**:
Replacement of a Daily plan that has no Work outcome by a new plan for the same date.
_Avoid:_ Re-plan

**Re-plan**:
A new Schedule revision for the unelapsed remainder of the current day's existing Daily plan.
_Avoid:_ Regeneration, replace plan

**No longer needed**:
A planned work session retained after its Task is finished or cancelled. It has no invented Work outcome or Actual minutes.

**Needs refresh**:
The state of a Daily plan whose captured effort assumptions no longer match the live Tasks.

## User Workflow

1. The user generates a Daily plan as in 1.2.0. Each ranked Task captures its whole-task estimate and its remaining effort at that moment.
2. From a work block on the dashboard or plan detail, the user records done, partly done, or skipped. The first worked outcome moves an Open Task to In progress.
3. If the provisional result exhausts an unfinished Task, the same dialog asks the user to finish it or enter a positive remainder. Cancelling the dialog saves nothing.
4. The user may log unplanned work for a current or past date, optionally reassessing what remains.
5. The user explicitly finishes a Task, or cancels it. Unused future sessions stay on their plans as no longer needed. A later day's generation includes only work that is still plannable, using its current remainder.
6. If recorded progress makes an existing plan's captured effort stale, the plan stays unchanged and offers a refresh. Refreshing a plan with no outcomes regenerates it. Refreshing the current day after outcomes exist re-plans it.
7. Re-planning asks the user to resolve every unresolved elapsed block first. For a block crossing the cutoff, the user enters the minutes worked so far and explicitly assesses what remains. The client supplies the current date and cutoff; the server does not infer them.
8. The re-plan ranks all current plannable Tasks, schedules the shrunk window, and appends a revision. Earlier revisions and their outcomes remain available on plan detail.
9. Plan history and the day view report known actual minutes separately from planned minutes, and they count blocks whose actual time is unknown.

## Progress And Remaining Effort

### Initialization

Creating a Task copies its whole-task estimate into its remaining effort. An absent estimate leaves remaining effort unknown. Before any progress exists, editing that estimate on an Open Task updates the remaining effort to match. Progress exists when the Task has any work outcome, unplanned work, remaining-effort checkpoint, or status other than Open. After that, editing the whole-task estimate preserves it for comparison and does not change the remainder.

### Provisional credit

A work outcome changes remaining effort only when the remainder is already known and the save does not include an explicit reassessment:

| Outcome | Actual minutes | Provisional credit |
|---|---|---|
| Done | Optional positive value | Planned duration of that block |
| Partly done | Required positive value | The entered actual minutes |
| Skipped | Omitted | Zero |

A done block finished in 35 minutes but planned for 50 therefore leaves the Task 50 minutes closer to done when no reassessment is entered. The 35 minutes are actual time, not the progress credit. Omitted actual minutes stay unknown; they are never stored or displayed as zero, and they are never backfilled from the planned duration.

Skipped means no work was done. Any positive amount of work is partly done, not skipped.

Unknown remaining effort stays unknown until the user assesses it. Unplanned work follows the same credit rule: its required positive actual minutes provisionally reduce a known remainder, while an unknown remainder stays unknown.

### Checkpoints

An explicit remaining-effort value, including an explicit unknown value, is a checkpoint. Finishing a Task checkpoints zero. Reopening checkpoints the fresh assessment. Reconciling a crossing block also requires a checkpoint.

Events that affect a Task are ordered by work date. Events on the same work date are ordered by the time they were first recorded. Correcting an entry does not give it a new position in that order.

The current remainder starts from the whole-task estimate, or from unknown when there was none. The latest checkpoint replaces the value calculated so far. Only progress strictly after that checkpoint applies further provisional credit. Progress before the checkpoint remains visible in history and in actual-minute totals.

A checkpoint and the work in the same save are one assessment: the explicit value is the result, and that work does not also receive provisional credit. The dialog states the same-day limitation: work logged later for that same date counts as new progress. If the reassessment already included such work, the user corrects the remainder again. The product does not collect actual start and end times, so it cannot reconstruct their order within the day.

### Exhausted estimates

If provisional credit would reduce a known remainder to zero or below, and the same save does not finish the Task or provide a positive checkpoint, the save is rejected and nothing changes. Reaching zero is a prompt to finish the Task or reassess it. It is not automatic completion and does not leave an unfinished Task with an unschedulable zero.

### Dates

The client supplies the current wall-clock date. Progress may be created or corrected when its work date is before or equal to that date, including a current-day block whose planned start has not arrived. A future work date is rejected. The server does not substitute its own date for that decision.

## Task Lifecycle

Recording a done or partly done outcome, or unplanned work, moves an Open Task to In progress. Skipped work does not by itself start the Task. The existing manual status control may still mark it In progress; that manual change grants no progress credit.

Finish Task is explicit. It sets the status to Done and the remaining effort to zero. It may be submitted alone or in the same save as the work that exhausted the estimate. Cancellation keeps the current remainder, including an unknown remainder, and removes the Task from future planning.

Reopening a Done or Cancelled Task to Open or In progress requires a fresh positive remainder or an explicit unknown assessment in the same save. The previous history stays. Reopening does not restore the pre-completion remainder or reset it to the whole-task estimate.

Once a Task has a work outcome or unplanned work, its status cannot return to Open. Done and Cancelled remain available through their explicit actions.

While a Task is Done or Cancelled, each of its unused planned work sessions is shown as no longer needed. Those sessions gain neither an outcome nor actual minutes. They are not actionable and do not have to be reconciled before re-planning. Sessions that already have outcomes remain correctable under the checkpoint rules.

Deleting a Task removes its live remainder and its future planning eligibility. It preserves source identity, plan snapshots, work outcomes, unplanned work, and checkpoints. Those historical rows retain the immutable source-task identity and lose only their optional live reference, as task snapshots already do.

## Carry-over And Freshness

Generating a Daily plan loads the owner's current plannable Tasks. In-progress work remains must-continue work, and the existing due/overdue and optional rules are unchanged. The quantity offered to the scheduler is the Task's current remaining effort, not its whole-task estimate. Unknown effort is unplaced with `NO_ESTIMATE`. A positive remainder that cannot fit is unplaced with `OUT_OF_TIME`.

There is no carried-over copy of a Task and no scheduled generation of the next day. A block's presence in a plan does not reduce remaining effort; only saved progress does. The same Task may appear in several dates' snapshots, each retaining the effort captured for that revision.

A revision is stale when one of its actionable Task snapshots no longer matches the live Task's remaining effort, or when an actionable work block belongs to a Task that is no longer plannable. Adding a new Task does not by itself make an existing plan stale. Preference and commitment edits keep the 1.2.0 behavior: they do not persistently invalidate a saved schedule, and the client may offer a session-local refresh when it knows about the edit.

A stale plan is not rewritten automatically. Its captured blocks remain the schedule until the user regenerates an outcome-free plan or re-plans a current plan that has outcomes.

## History Protection

Regeneration keeps the 1.2.0 compare-and-replace behavior only while the plan has no work outcome. Any outcome, including skipped, refuses regeneration before a provider call. The appropriate refresh is then re-planning, and only when this milestone's re-plan rules allow it.

The same condition refuses plan deletion. A plan whose only additional marking is no longer needed, and which has no outcome, may still be replaced or deleted.

Outcome-bearing blocks on elapsed history remain correctable. A future block that a newer revision superseded, and which has no outcome, is read-only. Work done despite that superseded plan is recorded on an actionable current block or as unplanned work, not as a second outcome on the abandoned block.

A block completed early keeps its outcome. Re-planning does not treat it as unresolved, does not remove its credit, and does not create another actionable copy. If its planned interval is entirely after the cutoff, the composed rail uses the new revision there; the early result remains in the day's recorded-work summary and in revision history.

## Mid-day Re-planning

Re-planning is available only for the client's current date and only for a Daily plan whose generation captured the full scheduling snapshot defined below. The client supplies the cutoff time. A cutoff earlier than the original window start is clamped to that start. A cutoff at or after the original window end is rejected. The user records actuals and carries unfinished work forward instead of extending the day.

Before the provider is called, every work block on the actionable revision must be resolved when its planned end is at or before the effective cutoff, unless it is no longer needed or already has an outcome. A block that starts before the cutoff and ends after it is a crossing block. Its reconciliation asks for known actual minutes of zero or more and a required remaining-effort checkpoint. It must not be marked done for its original planned duration. Zero actual minutes means no work was done during the elapsed portion; that known zero is distinct from an omitted actual. The save stores the minutes and checkpoint, and marks the block so ordinary done-credit cannot be applied later.

The provider then ranks every current plannable Task, including Tasks added or changed since the original generation, under the existing must-include ordering rules. The ranking input shows current remaining effort. The candidate limit, validation, and provider-failure behavior are unchanged: more than 100 candidates is a coded client error, and a provider failure saves no revision.

The placement window runs from the effective cutoff through the original window end. It uses the plan's captured cadence, minimum session, trailing-buffer request, and fixed breaks. It reloads the owner's commitments for that date. The focus calculation starts over at the cutoff. The response and confirmation copy say that the new stretch is a planning reset, not a record that the user took a restorative break. The latest free minutes inside the shrunk window are reserved as buffer, and that revision records both the requested and realized amounts. An unavailable remainder may place nothing and leave the work unplaced. The window never extends past its original end.

The new result is appended as the next schedule revision of the same Daily plan. The plan identity, original window, earlier revisions, outcomes, and checkpoints remain. Only the latest revision is actionable.

## Day View Composition

The dashboard shows one non-overlapping planned rail for the current actionable day:

- Planned intervals that ended at or before the latest revision's cutoff come from the revision that was in effect then, together with their outcomes.
- A reconciled crossing block contributes its elapsed planned portion, `[start, cutoff)`, to that rail. Its actual minutes annotate the portion; they are not drawn as their own interval. The unelapsed planned portion appears only in revision history.
- Intervals at or after the cutoff come from the latest revision, including its breaks, commitments, buffer, and unplaced work.
- An early-completed block whose whole planned interval is after the cutoff is omitted from this rail and listed with the day's recorded work.

Plan detail can select any revision and show that revision's complete rail. Superseded future blocks are visible there and are not recordable.

Scheduled-work, free-minute, required-minute, and buffer figures shown for a revision count that revision alone. Day-wide actual minutes add each recorded actual once: known block actuals, including a reconciled zero, plus unplanned work for that date. Done blocks with omitted actuals contribute a missing-actual count, not a zero. Superseded blocks without outcomes contribute neither.

Session labels are derived from the work blocks in the view being rendered. The composed day and a single-revision view therefore number their own visible sessions.

## Scheduling Integration

`DailyPlanScheduler` continues to call the pure two-stage scheduler and then validate its postconditions. The only planning input that changes is the quantity on each ranked Task: current remaining effort for a new generation, or the remaining effort captured for the revision being built during re-planning.

For every positive-effort Task in a revision, the revision's scheduled work plus its `OUT_OF_TIME` minutes equals that revision's captured remaining effort. It does not have to equal the whole-task estimate, and it does not include work placed or completed in another revision. An unknown remainder still produces exactly one `NO_ESTIMATE` entry and no work block.

`requiredMinutes` for a revision is the sum of known remaining effort on must-include candidates at that planning operation. The shortfall warning continues to be derived from must-include unplaced rows. Its due-day meaning is explicit in the UI: this is work due on or before the planning date that the day did not fit. It does not predict whether a later due date will be missed.

Peak hours remain a shaded snapshot and are not a placement input. The owner-row lock still covers the short persistence transaction only. Provider calls stay outside the transaction.

## Data Ownership And Invariants

The Task owns its live whole-task estimate, remaining effort, status, and a monotonic effort version. A checkpoint, work outcome, or unplanned-work row is history owned by the user and identified by immutable source-task identity; deletion of the live Task does not delete that history.

A Daily plan still has one owner and one planning date. It owns one or more schedule revisions. Plan-task snapshots and blocks belong to a revision. The latest revision is the only actionable schedule. A revision's metrics and unplaced work belong to that revision.

The plan also owns the scheduling snapshot used for a later re-plan: work window, peak window, cadence state and lengths, minimum session, requested buffer, and fixed breaks. Commitments are not copied into that snapshot because re-planning reloads them.

Invariants:

- Open and In-progress Tasks have a positive remainder or an unknown remainder. Done Tasks have a known zero. Cancelled Tasks keep whatever remainder they had.
- A partly done outcome has positive actual minutes. An ordinary skipped outcome has no actual minutes. A crossing reconciliation has known actual minutes of zero or more and a checkpoint.
- A new or corrected progress record cannot move to another work date or ahead of an existing checkpoint by being edited.
- A revision's conservation check uses captured remaining effort, as defined above.
- Persistence of a re-plan or progress save checks the version or revision identity it was based on before writing.

## Schema And Migration

The next forward-only Flyway migration after `V4__scheduled_day_block_constraints.sql` is non-destructive. It does not delete Daily plans, Tasks, preferences, commitments, or users.

It adds:

- Live `remaining_effort_minutes` on Tasks, nullable, backfilled from the current whole-task estimate. Null remains unknown. A new monotonic effort version starts at zero for existing rows.
- A remaining-effort checkpoint history identified by owner, immutable source Task, work date, recording time, and assessed remainder. Its live Task reference is nullable and clears if the Task is deleted.
- Revision identity and revision-specific copies of the existing schedule metrics. Every current Daily plan receives one initial revision containing its current plan tasks, blocks, and metrics. Absence of a cutoff means the original window start.
- Revision ownership for plan tasks and blocks, backfilled to that initial revision.
- Nullable block-progress fields: outcome, actual minutes, recording time, progress version, and a reconciliation marker. Existing blocks have no outcome.
- Unplanned-work rows with owner, source Task, work date, positive actual minutes, recording time, and a nullable live Task reference.
- Nullable scheduling-snapshot fields and fixed-break snapshot rows on the Daily plan. They stay null for plans migrated from 1.2.0. Generation after this migration fills them. The migration must not invent cadence or fixed-break history from current preferences.

Plan-level schedule metrics remain available to the API as the latest revision's values. The stored revision is the source of those values; a second independently updated copy must not be able to drift.

## API Contract

All new mutating operations use the existing session and CSRF rules. Error responses keep the shared body and add a stable `code` where a client must branch. The frontend branches on the code, then refetches the affected resource. New codes are:

| Code | When |
|---|---|
| `PLAN_HAS_PROGRESS` | Regeneration or deletion targets a plan with any work outcome. |
| `PLAN_CHANGED` | A re-plan's expected revision, candidate set, or captured effort versions is stale. |
| `PROGRESS_CONFLICT` | A progress, unplanned-work, or effort save names a stale effort or progress version. |
| `ELAPSED_WORK_UNRESOLVED` | Re-plan is requested before elapsed work is resolved. |
| `REPLAN_LEGACY_SNAPSHOT` | The plan has no complete scheduling snapshot. |
| `REPLAN_NOT_TODAY` | The plan date is not the client-supplied current date. |
| `REPLAN_WINDOW_ENDED` | The cutoff is at or after the original window end. |
| `FUTURE_ACTUAL` | The work date is after the client-supplied current date. |
| `REMAINDER_UNRESOLVED` | Provisional credit would exhaust the remainder without finish or a positive reassessment. |
| `BLOCK_NOT_RECORDABLE` | The block is superseded, no longer needed, or otherwise not open for a new outcome. |

Validation failures that only restate malformed input, such as negative minutes or a non-aligned time, remain ordinary client errors. A provider failure remains **502** and persists nothing. A vanished source Task during planning remains `TASK_MISSING_DURING_GENERATION`.

### Tasks

Task responses add `remainingEffortMinutes`, where null means unknown, and `effortVersion`. Creating a Task initializes both effort fields as defined above.

The existing Task update changes the whole-task estimate. It also updates the live remainder only while the Task is still Open and has no progress. A status change follows the lifecycle rules. Done finishes the Task. A transition out of Done or Cancelled requires `remainingEffortMinutes` in that request: a positive number, or null when the user explicitly chooses unknown. A stale `effortVersion` returns `PROGRESS_CONFLICT`.

A dedicated remaining-effort command accepts a positive value or explicit null, the expected effort version, and the client current date. It writes a checkpoint on that date.

### Block progress

Scheduled-block responses add a persistent block id, revision id, outcome, actual minutes, reconciliation marker, progress version, and display state: actionable, historical, superseded, or no longer needed.

Recording or correcting progress identifies the block and expected progress version. The body carries the outcome, any actual minutes, the client current date, and optionally a remaining-effort checkpoint or finish request. A crossing reconciliation uses the same command with known actual minutes and a required checkpoint. Success returns the updated Task effort and the affected plan.

### Unplanned work

The user can create, correct, and delete an unplanned-work entry by its id. Creation requires a Task, a work date, positive actual minutes, the client current date, and the expected effort version, with an optional checkpoint. Correction and deletion use their expected version. The entry appears in plan and date views but never as a placed block.

### Planning

Generation still accepts the planning date and optional replacement id. Before calling the provider it refuses an outcome-bearing plan with `PLAN_HAS_PROGRESS`. On success it creates the initial revision and fills the scheduling snapshot. If live effort changes while the provider is running, generation still saves the snapshot it captured, as 1.2.0 does for ordinary edits; the resulting plan is then flagged stale. This tolerance does not apply to re-planning.

Re-planning accepts the client current date, cutoff, expected revision id, and the candidate effort versions it read. It returns the same plan id with a new latest revision. A stale check at persistence returns `PLAN_CHANGED` and leaves the prior revision actionable. The provider is not held inside the owner lock.

Plan detail includes the revisions, the composed current rail, day-wide known actuals and missing-actual count, unplanned work for that date, and whether the latest revision needs refresh. Summaries use the latest revision for schedule counts and warning state, and add whether the plan has progress and needs refresh. They do not sum superseded revisions into scheduled work.

## UI Behavior

The dashboard and plan detail make work blocks with an actionable or correctable historical state open the same outcome dialog. The dialog shows the planned duration, any known actual duration, and the current remaining effort. It does not present an empty actual field as zero. When the provisional result would exhaust the Task, the primary save stays unavailable until the user chooses Finish Task or enters a positive remainder.

The composed rail keeps the 1.2.0 visual language for planned work, breaks, commitments, buffer, and peak shading. Outcomes are annotations on those planned blocks. A separate recorded-work region lists known actual minutes, the missing-actual count, early completions that are off the composed rail, and unplanned work. No-longer-needed sessions use that literal state and are not given outcome controls.

Plan detail adds a revision choice. Selecting an earlier revision shows its own rail and identifies superseded future blocks as read-only. The dashboard does not expose revision browsing; it shows the composed current plan.

The existing replacement dialog remains for outcome-free regeneration. A plan with progress instead explains that recorded work is kept and, when re-planning is legal, offers Re-plan remaining day. That confirmation states the cutoff, that commitments will be reloaded, and that the focus stretch restarts without recording a break. A legacy plan with progress explains that today's shape cannot be re-planned because its original scheduling rules were not captured; the user can continue recording actuals and carry unfinished work to another day.

A stale plan shows a refresh notice rather than silently changing. Conflict responses close the in-flight action, refetch, and explain that a newer change was kept. The shortfall warning names the due or overdue work that did not fit this day.

## Concurrency And Failure

Progress saves, effort reassessments, finish and reopen, unplanned-work changes, and re-plan persistence lock the owner row only while they recheck versions and write. Two overlapping progress saves cannot both succeed: the later identity check fails with `PROGRESS_CONFLICT` and the first write remains.

A re-plan captures its revision and candidate effort versions before the provider call. Progress or a competing re-plan may commit while that call is running. The returning re-plan rechecks under the owner lock, writes nothing on mismatch, and reports `PLAN_CHANGED`. A provider or validation failure also writes no revision. Reconciliation already saved before the call is real progress and stays saved; failure does not roll the day back to an unresolved state.

An exhausted-remainder save is atomic. If finish or a positive checkpoint is absent, neither the outcome nor the effort changes. The same applies to a reopen that omits its fresh assessment and to a crossing reconciliation that omits either actual minutes or a checkpoint.

## Upgrade

Existing plans, blocks, preferences, commitments, and Tasks remain in place. Backfilled remaining effort matches each Task's current estimate, so an unstarted Task behaves as it does today. Existing plans receive one revision and no outcomes.

Those migrated plans have no scheduling snapshot. Users may record progress on them. Re-planning returns `REPLAN_LEGACY_SNAPSHOT`. If such a plan still has no outcome, the user can regenerate it; the replacement captures a complete snapshot and can later be re-planned. If outcomes were recorded on the legacy plan first, regeneration is also unavailable. That limitation is accepted: the product will not fill in historical cadence or fixed breaks from current preferences. The user continues recording actuals, and later-day generation carries the unfinished remainder.

## Acceptance Scenarios

- A 50-minute block is marked done with 35 actual minutes and no reassessment. The Task receives 50 minutes of credit, reports 35 known actual minutes, and moves from Open to In progress when it was Open.
- The same block is marked done with actual minutes omitted. Credit is still 50. The day reports one missing actual, and neither the total nor the block displays those minutes as zero.
- A partly done block requires a positive actual value and credits that value. A skipped block credits nothing and records no actual minutes.
- A Task with an unknown remainder gains an outcome or unplanned work. Its remainder stays unknown, and planning leaves it unplaced as `NO_ESTIMATE`, until the user assesses it.
- Twenty minutes remain and the user logs 30 minutes partly done without finishing or entering a new positive remainder. The request fails and leaves both the block and the Task unchanged. Repeating it with either finish or a positive remainder saves both changes.
- The user checkpoints 90 minutes on Tuesday, then on Wednesday logs Monday's work. Monday's actuals appear in Monday's history, and Tuesday's 90-minute assessment remains current. Another entry for Tuesday recorded after that checkpoint does reduce the 90 minutes. The checkpoint dialog explains this same-day ordering limit.
- Correcting Monday's actual minutes after Tuesday's checkpoint updates Monday's reported actuals and does not move the entry later in order. A done block's actual-minute correction does not change its planned-duration credit.
- Wednesday's generation includes an unfinished Task once, using Wednesday's current remainder. Tuesday's scheduled but unrecorded block did not reduce that remainder. In-progress work still ranks before newly started work.
- Wednesday's plan is generated, then more work is recorded Tuesday. Wednesday's plan keeps its blocks and shows that it needs refresh. No provider call starts until the user asks.
- Finishing a Task sets its remainder to zero and labels its unused sessions no longer needed. Those sessions do not block a later re-plan and do not gain skipped outcomes. Cancelling instead keeps the remainder but removes the Task from planning. Reopening requires a new positive or explicitly unknown remainder and keeps the old outcomes.
- Deleting a finished Task removes it from future candidate lists and keeps its historical snapshots, actuals, and checkpoints.
- At 14:00 the user re-plans with an unresolved 09:00 block and a 13:30–14:30 block. The operation is refused. After recording the elapsed block and reconciling the crossing block with 20 actual minutes and an explicit remainder, the re-plan ranks current Tasks into 14:00 through the original window end. The crossing block does not receive 60 minutes of done credit.
- The user repeats re-planning at 16:00. Both earlier revisions and their outcomes remain, and only the newest remainder is actionable. A 15:00 block from the first revision, now superseded and never recorded, rejects a new outcome.
- A commitment added after the original generation appears in the re-plan because commitments are reloaded. The captured fixed breaks and cadence do not silently change to newer preference values. The new revision says the focus stretch restarted and does not show that restart as a break that was taken.
- The cutoff is before the window, so placement starts at the original window start. The cutoff is equal to the window end, so re-planning is rejected. The remaining window has no free time, so the revision is saved with its work unplaced and the original end unchanged.
- The user completes a later block before its planned start. A subsequent re-plan keeps that credit and does not demand reconciliation for that block. The new rail does not paint a second actionable copy over its interval.
- One tab saves progress while another tab's re-plan is waiting on the provider. The progress save succeeds and the re-plan returns `PLAN_CHANGED` without replacing the revision. Two tabs saving the same block or remainder produce one success and one `PROGRESS_CONFLICT`.
- A provider failure during re-planning leaves the previous revision and any already saved reconciliation intact.
- After upgrade, an existing plan can accept progress and cannot be re-planned. Regenerating it before any outcome captures a scheduling snapshot. Recording an outcome on the migrated plan first leaves both regeneration and re-planning unavailable, without fabricated historical settings.
