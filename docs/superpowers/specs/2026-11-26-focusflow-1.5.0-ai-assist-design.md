# FocusFlow 1.5.0 Design — Rule-based Ranking and AI Assist

Date: 2026-11-26

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Previous milestone:** `docs/superpowers/specs/2026-10-11-focusflow-1.4.0-dependencies-horizon-design.md`
**Roadmap:** `docs/superpowers/roadmap.md`

Decisions introduced here are recorded as [ADR 0036](../../adr/0036-rule-based-ranking.md). It supersedes [ADR 0006](../../adr/0006-ai-total-ordering.md) and [ADR 0022](../../adr/0022-bound-ai-ranking-requests.md). The other decisions in ADRs `0002` through `0035` remain in force.

## Purpose

Today the model ranks every candidate on generate and re-plan, but the ranking prompt is a comparator written in English: priority, then due date, then block, with blockers first. Java already validates the result and repairs dependency order. The horizon forecast uses a separate fixed comparator that sorts **due date before priority**, while the prompt asks for **priority before due date**, so the forecast can disagree with the plan generate produces.

1.5.0 does two things:

1. **Part A.** Generate and re-plan rank with one Java comparator shared with the horizon. The model leaves the generate path.
2. **Part B.** The model is used where rules cannot work: reading text. The first feature is an estimate suggestion for tasks with no estimate, grounded in the user's own finished work.

This is a design document, not an implementation plan.

## Goals And Non-Goals

Goals:

- One ordering function used by generate, re-plan, and the horizon: identical ranking inputs produce the same repaired order. This does not promise identical schedules.
- Generate and re-plan never call a provider and never return 502. The app plans fully with no API key.
- A generic completion client that carries the existing timeout, bounded retry, `Retry-After`, and metrics behaviour, reusable by later AI features.
- A suggested estimate for a task with no estimate, which the user reviews and saves through the existing task update. Nothing is written by the suggestion.
- AI features are hidden when no API key is configured.

Non-goals:

- No AI-ranking option or toggle. The model is not on the generate path in any mode.
- No rewriting or relabelling of plans saved under the old ranking. Plans are snapshots.
- No bulk "estimate all", no embeddings, and no new database tables or migrations.
- No split-into-steps, natural-language capture, or blocker hints. They are later sub-projects that build on this foundation.
- No removal of `PLAN_CANDIDATE_LIMIT`. It stays at 100 in this milestone.
- No distributed rate limiting. The limit is in memory and per instance.
- No chat surface over the app.

## Part A — Java ranks the plan

### Shared comparator

Move the ordering in `HorizonForecaster` (`orderCandidates`, the sort followed by `DependencyOrderRepair.repair`) into one class, `dependency/CandidateOrdering`. It takes the inherited assignments, the links, and a lookup for priority, and returns the repaired id order plus the group per task.

Order within the whole candidate list:

1. ranking group: must-continue, due-or-overdue, optional
2. inherited due date, earliest first, undated last
3. priority: HIGH, MEDIUM, LOW
4. task id, ascending, as a stable tiebreak

Then `DependencyOrderRepair.repair` runs on that list. This is the order the horizon already uses; its results do not change.

The guarantee applies when the candidate ids, inherited assignments (groups and due dates), priorities, and dependency links are identical. The horizon may use different inputs: for example, projected work on an earlier day can make an Open task must-continue on a later forecast day, while generating that day's plan uses live task state. Saved plans remain snapshots. Different inputs, availability, or placement constraints can therefore produce different orders or schedules.

Known trade-off: an undated HIGH task sorts after every dated LOW task in the same group. This is accepted for 1.5.0 and noted in the ADR.

### Service changes

- `DailyPlanService.generate` and `replan` call `CandidateOrdering` instead of `aiClient.generate` followed by `applyAiRanking`.
- A `BrokenDependencyOrderException` from repair is an internal error (500). The links are acyclic by construction, so it indicates a bug, not a provider fault.
- `PlanPipelineResult` keeps `rankedTasks` and the positioned items that the persister stores.
- `AiPlanItem` is renamed `RankedPlanItem` and moves out of the `ai` package.

### Removed

`DailyPlanAiClient`, `OpenAiDailyPlanClient`, `DailyPlanPromptBuilder`, `AiDailyPlanRequest`, `AiDailyPlanResponse`, `AiPlanTask`, `DailyPlanRankingValidator`, `RankingRejectionReason`, and the test configuration `DailyPlanAiTestConfiguration`. The `RankingRejectionReason` constructors on `AiProviderException` go with them.

### Unchanged

Saved plans, snapshots, `PLAN_CANDIDATE_LIMIT`, the scheduler, placement, and the horizon's results.

### API and docs

- `POST /api/daily-plans/generate` and `POST /api/daily-plans/{id}/replan` no longer document 502.
- `api.md` generate description changes from "The AI returns a total ordering" to "Java ranks candidates".
- `architecture.md`, the README, and the roadmap "Who schedules" paragraph are updated.
- ADR 0036 is added; ADR 0006 and 0022 are marked superseded.

## Part B — AI assist foundation

### Completion client

`ai/CompletionClient` has one method: `String complete(String feature, String prompt)`, returning the message content. `OpenAiCompletionClient` takes over the existing request, retry, `Retry-After`, and error-classification code from `OpenAiDailyPlanClient`.

Metrics are `focusflow.ai.requests` (timer), `focusflow.ai.retries`, and `focusflow.ai.failures`, each tagged `feature`. This replaces the hard-coded `focusflow.ai.generate`.

Each feature owns its prompt builder, response record, JSON parsing, and validation. Parsing stays in Java.

### Availability

- The completion client and the AI services are created only when `focusflow.openai.api-key` is non-blank.
- `GET /api/capabilities` returns `{ "aiAssist": true | false }`. It requires a session.
- The frontend hides AI controls when `aiAssist` is false.
- If an AI route is called while disabled, it returns 503 with code `AI_ASSIST_DISABLED`.

### Errors

Per [ADR 0020](../../adr/0020-machine-readable-error-codes.md), AI routes return coded errors:

| Status | Code | When |
|---|---|---|
| 502 | `AI_UNAVAILABLE` | Provider call failed after retries, or timed out |
| 502 | `AI_INVALID_RESPONSE` | Output is not valid JSON, or fails validation |
| 429 | `AI_RATE_LIMITED` | Per-owner limit exceeded |
| 503 | `AI_ASSIST_DISABLED` | No API key configured |

A failed AI call affects only that call. Task create, edit, and generate keep working.

### Rate limit

An in-memory sliding window per owner, shared across all AI features, limits successful suggestions. The default is 30 per hour, configurable as `focusflow.ai.rate-limit.per-hour`. Atomically reserve a slot immediately before the first provider attempt; an in-flight reservation occupies capacity, so concurrent requests cannot oversubscribe the limit. If no slot is available, reject the request with `AI_RATE_LIMITED` before calling the provider. Retries belong to the same reservation.

A validated suggestion consumes one slot, even if the user never saves it. Start its one-hour window when validation succeeds. Release the reservation on provider failure, timeout, invalid response, or other failure; invalid input and requests rejected before the provider call consume nothing. Ensure all failure paths release reservations. The limit is per instance; the app is single-instance today.

This revisits the deferred "Generate rate limiting" item for AI assist only. It is not a provider-spend cap: repeated failed requests can still incur costs. A separate failure cooldown or attempt limit is deferred; bounded retries and failure metrics remain in place.

### Estimate suggestion

`POST /api/tasks/estimate-suggestion`. It takes text rather than a task id, because the create form has no id yet. It writes nothing and does not take the owner lock.

**Request**

| Field | Type | Required | Notes |
|---|---|---|---|
| `title` | string | yes | non-blank, at most 255 characters |
| `description` | string | no | truncated to 500 characters in the prompt |
| `excludeTaskId` | integer | no | when editing, excludes that task from history |

**History.** `EstimateHistoryQuery` returns up to 20 of the owner's `DONE` tasks, newest first, that have an estimate and complete actual minutes:

- Each performed work contribution counts once across revisions; use its recorded actual minutes, never the planned duration. Unplanned work counts toward the actual total.
- A skipped block is not performed work and does not disqualify the task. Exclude a task if any performed contribution is missing `actualMinutes`, or if it has no recorded work contribution.
- Tasks have no finished-at timestamp. Order by the latest original recording instant among performed contributions: `firstRecordedAt` for planned work and `recordedAt` for unplanned work. Corrections and skips do not promote a task. Break equal instants by task id ascending. A task completed entirely with unplanned work is eligible.
- If there is no usable history, the call still works from the task text alone.

**Prompt.** The task title and truncated description, then one line per history task: `H<taskId>: <title> | estimated=<n> | actual=<n>`. The model is told to reply with JSON only: `{"minutes": <int>, "reason": "<text>", "basedOnTaskIds": [<id>, ...]}`.

**Validation** (`EstimateSuggestionValidator`):

- `minutes` is an integer from 1 to 2400, rounded to the nearest 5 and not below 5.
- `reason` is trimmed and cut to 280 characters; blank is invalid.
- `basedOnTaskIds` entries not in the history that was sent are dropped and counted in a metric; they do not fail the call, because they are display-only.
- Anything else is `AI_INVALID_RESPONSE`.

**Response**

```json
{
  "minutes": 90,
  "reason": "Similar writing tasks took about 90 minutes.",
  "basedOn": [
    { "taskId": 12, "title": "Write Q2 report", "estimatedMinutes": 60, "actualMinutes": 95 }
  ]
}
```

`basedOn` figures come from the database, not from the model's text.

**Acceptance.** The user edits the number if they want and saves through the existing task update. That path already rejects a non-positive estimate and, while the task is untouched, copies the estimate into remaining effort. No new write path exists.

### Frontend

- The task create and edit forms get a "Suggest with AI" button beside an empty whole-task estimate field. Beside it, disclose that the task text and up to 20 past task titles and durations are sent to the provider. Only clicking that button requests a suggestion. A valid response fills the field and shows the reason and "similar to" chips; the user can edit before saving.
- Do not overwrite an intervening manual edit. Autofill only if the same task or draft is still open, its title and description are unchanged, and the estimate is still empty and untouched since the click; otherwise ignore the stale response.
- A saved `NO_ESTIMATE` row retains its historical reason. Offer a corrective action only if its source task still exists, is plannable, and still has unknown remaining effort; check live eligibility again on opening. For an untouched Open task whose estimate update would initialize remaining effort, "Add estimate" opens the editor without requesting a suggestion. Otherwise, offer the existing manual "Set remaining effort" action. Do not infer remaining effort from a whole-task estimate and recorded actuals. Deleted, finished, or already-resolved tasks have no corrective action.
- On failure the form shows an inline error and stays usable.
- When `aiAssist` is false, hide AI controls and suggestion details, not the manual Today actions or the ordinary task editor.

### Privacy

Past task titles and their durations are now sent to the provider, not only the tasks being planned. The README and `.env.example` state this beside the API key setting.

## Testing

- **Comparator:** port the ordering cases from the horizon tests; verify identical candidates, assignments, priorities, and links give the same order from generate, re-plan, and the horizon. Cover projected progress producing different later-day inputs without treating the resulting difference as a failure.
- **Service:** rewrite `DailyPlanServiceTest` around real orderings instead of stubbed AI responses; assert generate and re-plan make no provider call.
- **Completion client:** port `OpenAiDailyPlanClientTest` (retry, `Retry-After`, timeout, error mapping, metric tags).
- **Estimate:** parser and validator unit tests (bounds, rounding, unknown basis ids, missing fields); history integration tests for missing performed-work actuals, skips, several revisions, unplanned-only work, exclusion of the edited task, recording-time ordering, corrections, timestamp ties, and the 20-task limit.
- **Rate limit:** cover concurrent reservations at capacity, expiry, retries counting as one request, successful suggestions counting without a save, and release after provider failure, timeout, invalid output, and pre-provider rejection. Verify a rejected concurrent request makes no provider call.
- **Controllers:** 429, 502 (both codes), and 503; 401 without a session; the route writes no rows.
- **Capabilities:** flag follows the key.
- **Frontend:** AI button hidden without a key while manual actions remain; disclosure and explicit suggestion click; eligible suggestion fills the field; stale responses do not overwrite edits or another draft; errors stay inline. Cover untouched versus previously worked tasks, stale or deleted source tasks, and live eligibility rechecking for `NO_ESTIMATE` rows.

## Later sub-projects

Each gets its own spec. All build on `CompletionClient`, the capability flag, and the rate limit.

- **Natural-language capture.** Text in, a draft task out; the client supplies the current date.
- **Split into steps.** Needs a batch create endpoint in one transaction, a decision on cancelling the original so its effort is not counted twice, and relinking existing dependents to the final step.
- **Blocker hint for one task**, run at create or edit time rather than across all pairs.

A read-only AI explanation of a shortfall is deliberately not planned: the warning data is already structured, and a template says it without a provider call.
