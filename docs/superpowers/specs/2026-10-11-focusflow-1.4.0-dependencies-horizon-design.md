# FocusFlow 1.4.0 Design — Dependencies and the Multi-day Horizon

Date: 2026-10-11

**Parent spec:** `docs/superpowers/specs/2026-05-14-focusflow-ai-design.md`
**Previous milestone:** `docs/superpowers/specs/2026-10-02-focusflow-1.3.0-progress-carry-over-design.md`

Decisions introduced here are recorded as [ADR 0028](../../adr/0028-inherited-dependency-urgency.md), [ADR 0029](../../adr/0029-repair-dependency-order.md), [ADR 0030](../../adr/0030-blocked-unplaced-reason.md), [ADR 0031](../../adr/0031-derived-horizon-forecast.md), [ADR 0032](../../adr/0032-working-weekdays-for-horizon.md), and [ADR 0033](../../adr/0033-finished-blockers-release.md). ## Purpose

1.3.0 plans one day, records progress, and carries unfinished remaining effort into the next day the user generates. It cannot say that one task has to finish before another, and it cannot show whether a later due date will be missed.

1.4.0 adds finish-to-start dependencies to daily planning, then a read-only seven-working-day horizon that reuses the existing scheduler. The horizon is calculated when it is viewed. Daily plans remain the only saved schedules.

This is a design document, not an implementation plan. It assumes 1.3.0 is already built: remaining effort, schedule revisions, the composed day rail, and revision-preserving re-planning.

The work is one milestone in two slices. Dependencies can ship before the horizon. The horizon consumes the dependency rules and is not a second product.

## Goals And Non-Goals

Goals:

- Let the owner link tasks with finish-to-start dependencies, reject self-links, duplicates, and cycles, and show the links on the task form and task list.
- Treat Done and Cancelled blockers as released while keeping the link. Reopening the blocker makes it block again.
- Give a blocker the urgency of the plannable work waiting on it, so must-include order and dependency order agree.
- Ask the model for that inherited order, then repair remaining dependency inversions in Java before placement.
- Leave a task unplaced as `BLOCKED` when an active blocker in the same ranking is not fully placed, including a blocker with unknown remaining effort.
- Snapshot the dependency links used for a revision, and explain blocked and inherited work from that snapshot.
- Add working weekdays to scheduling preferences, defaulting to Monday through Friday, and use them only for the horizon.
- Show the next seven working days as a horizontal Gantt. Saved daily plans occupy their dates. Other working days are a fixed-rule forecast.
- Assume unrecorded sessions on saved plans are completed as planned, and forecast each later day from the effort that assumption leaves.
- Report whether due work is on track, at risk, overdue, beyond the horizon, or impossible to forecast.

Non-goals:

- No persisted multi-day plan, no saved horizon snapshot, and no separate "re-plan the week" command. Refreshing the horizon is another read.
- No AI call for the horizon, and no per-day provider ranking.
- No history-based pace. The forecast assumes work is done as planned.
- No change to daily-plan generation on non-working days. Working weekdays do not reject a generate.
- No start-to-start, finish-to-finish, or lead/lag dependencies. One link means finish-to-start.
- No subtasks, recurring tasks, or rolled-up parent estimates.
- No drag-to-reschedule, manual block editing, or a chart library.
- No refusal of progress on a blocked task. The schedule waits; the outcome dialog does not.
- No expansion of `needsRefresh` to cover dependency edits. A saved plan keeps the links it captured.
- No change to cadence, minimum session, fixed breaks, commitments, trailing buffer, the hard window end, or peak-window display.
- No new authentication, CSRF, or Flyway-policy design. New conflicts use the existing coded-error contract.

## Domain Language

Terms below amend `CONTEXT.md`. Prefer the glossary when it disagrees with older specs.

**Task dependency**:
A finish-to-start link from a blocker to a blocked task. The blocked task cannot be scheduled until the blocker is finished.
_Avoid:_ Subtask, parent task

**Active blocker**:
A blocker whose live status is Open or In progress. A Done or Cancelled blocker releases the blocked task. The link stays.

**Inherited urgency**:
The ranking group a task receives from its own status and due date and from the plannable tasks it blocks, directly or through a chain. A blocker is at least as urgent as the work waiting on it.

**Blocked work**:
A plannable task left entirely unplaced because an active blocker in the same ranking was not fully placed.
_Avoid:_ Out of time, no estimate

**Working day**:
A weekday the owner includes in the horizon. It does not limit which dates can have a Daily plan.

**Horizon**:
The read-only forecast of the next seven working days, calculated from live tasks, current preferences, commitments, and saved Daily plans.
_Avoid:_ Multi-day plan, weekly plan

**Forecast day**:
A horizon day that has no Daily plan. Its placement uses fixed ordering rules and the existing scheduler.

**As-planned pace**:
The horizon assumption that an unrecorded work session on a saved Daily plan consumes its planned minutes, up to the task's live remaining effort.

## Dependencies

### Links

A dependency row belongs to the owner and names two of that owner's tasks: the blocker and the blocked task. The pair is unique. A task may block many tasks and may be blocked by many tasks. Deleting a task deletes every link in which it appears. Links are not copied onto the surviving task snapshots except through the revision snapshot defined below.

Cycle detection uses every link the owner has, including links whose blocker is Done or Cancelled. A cycle that is hidden by a finished task would reappear when that task is reopened. The check runs while the owner row is locked, together with the insert or delete, so two concurrent adds cannot each store one half of a cycle.

An active blocker is Open or In progress. Done and Cancelled blockers do not constrain ranking or placement. Finishing or cancelling a blocker releases its dependents on the next generate, re-plan, or horizon read. Reopening it to Open or In progress, which already requires a fresh remaining-effort assessment, makes the link active again.

Recording progress, unplanned work, or a checkpoint against a blocked task stays legal. The outcome dialog names the active blockers and still saves.

Adding or removing a link does not change `effortVersion` and does not mark any Daily plan as needing refresh.

### Urgency inheritance

Ranking groups stay the three groups from 1.0.2:

1. Must-continue: In progress.
2. Due/overdue: Open, with a due date on or before the planning date.
3. Optional: every other plannable task.

A task's inherited group is the most urgent group among itself and every plannable task reachable by following "blocks" links. Done and Cancelled dependents do not grant urgency. The task's stored status and due date stay unchanged. `mustInclude` on a new revision is true for inherited groups 1 and 2.

This is what keeps dependency order inside the existing block order. If B is due today and A blocks B, A inherits group 2 even when A has no due date. A then ranks with due work, before optional work, and the dependency rule can still put A before B. Without inheritance those two rules contradict each other, and the collision the roadmap left open is resolved in favor of the blocker.

`requiredMinutes` remains the sum of known remaining effort on inherited must-include tasks, including must-include tasks that end up blocked.

### API

All mutating dependency operations use the existing session and CSRF rules. Unknown or other-owner task ids return **404**.

| Method and path | Body | Success |
|---|---|---|
| `POST /api/tasks/{id}/blockers` | `{ "blockerTaskId": number }` | **200** `TaskResponse` |
| `DELETE /api/tasks/{id}/blockers/{blockerId}` | — | **204** |

`TaskResponse` gains:

- `blockedBy`: `{ taskId, title, status }[]`
- `blocks`: `{ taskId, title, status }[]`

Both lists include finished tasks so the form can show and remove a link that is not currently blocking. List and get both return them.

New codes:

| Code | Status | When |
|---|---|---|
| `SELF_DEPENDENCY` | **400** | `blockerTaskId` is the same task. |
| `DEPENDENCY_EXISTS` | **409** | That pair is already stored. |
| `DEPENDENCY_CYCLE` | **409** | The new link would make a task reachable from itself. |

A delete of a link that is not present is **404**. Validation failures that only restate a missing field stay ordinary client errors.

### Pure dependency package

`com.focusflow.dependency` holds the cycle check, inherited-group assignment, and stable reorder. It accepts plain values, not JPA entities or HTTP DTOs, and it does not call Spring. ArchUnit protects it the same way it protects `com.focusflow.schedule` and `com.focusflow.effort`.

`TaskQueryService` is the read facade for an owner's links. The plan feature does not touch the task dependency repository.

## Daily Planning

### Capture

Generate and re-plan load the owner's links with the plannable candidates, before the provider call. Inherited groups, the prompt, ranking validation, the repaired order, placement, `mustInclude`, and the revision's dependency snapshot all use that captured set.

The persisted rank is the repaired order, because that is the order placement walks. The raw model order is not stored.

The revision snapshot stores one row per captured direct link whose blocker and blocked task are both in that revision's candidate set. Later link edits do not rewrite it. A revision migrated from earlier milestones has no dependency rows, which means it was planned with no dependencies.

### Prompt and validation

Each candidate line gains two fields computed from the captured links:

- `block=must-continue`, `block=due-or-overdue`, or `block=optional`, using the inherited group.
- `blockedBy=` followed by the captured active blocker ids that are in the candidate set.

The ranking rules tell the model to use the labeled block rather than recompute it from status and due date, and to place a task after every id in its `blockedBy` list.

`DailyPlanRankingValidator` classifies candidates with those same inherited groups. It still rejects unknown ids, duplicates, missing candidates, and block-order violations. It does not reject a dependency inversion. Intra-group order remains the model's choice except for the repair below.

### Repair

After validation succeeds, Java produces a new permutation. Repeatedly take the not-yet-emitted candidate with the earliest original index whose captured active blockers in the candidate set are already emitted. The result is the placement order.

Because every active blocker inherits a group at least as urgent as the tasks it blocks, a block-ordered input can be repaired without moving a later group ahead of an earlier group. If a repair would do that anyway, planning fails as an invalid ranking: **502**, and nothing is saved. That failure is a broken invariant, not a user-correctable conflict.

Rejecting the model outright for a dependency inversion was considered and rejected. Dependency order is a hard constraint Java can apply without guessing, and a rejection would turn an intra-group mistake into a provider failure. Block-order violations are still rejected, as they are today. See ADR 0029.

### Placement

`WorkPlacementPlanner` gains the captured direct links among the ranked tasks. Before placing a task it looks at each active blocker that is also in the ranking:

- When every such blocker is fully placed, placement is unchanged. Fully placed means the blocker's scheduled minutes equal its known remaining effort and it has no unplaced row.
- Otherwise the task is blocked. It gets no work blocks. It gets one unplaced row with reason `BLOCKED`. Known remaining effort is stored in full as the unplaced minutes. Unknown remaining effort stores null minutes.

`BLOCKED` wins over `NO_ESTIMATE`. A blocked task with unknown effort is `BLOCKED`, not `NO_ESTIMATE`. A task is never partly blocked: either its blockers are fully placed and ordinary placement may still leave an `OUT_OF_TIME` remainder, or the task contributes no sessions at all. A gap before an unfinished blocker is not available to the blocked task.

An unestimated blocker is not fully placed, because it has a `NO_ESTIMATE` row and no sessions. Tasks it blocks therefore stay `BLOCKED` instead of sliding into the time the blocker skipped. That is the scheduler change this milestone requires. The cursor-only behavior would schedule them.

The postcondition validator gains two conservation cases and one order check:

- Known remaining effort and `BLOCKED`: exactly one `BLOCKED` row, unplaced minutes equal to that effort, and no work blocks.
- Unknown remaining effort and `BLOCKED`: exactly one `BLOCKED` row with null minutes, and no work blocks.
- Unknown remaining effort and not blocked: the existing single `NO_ESTIMATE` row.
- Known remaining effort and not blocked: the existing rule, scheduled minutes plus `OUT_OF_TIME` minutes equals the captured remaining effort.
- When both a task and its captured active blocker have work sessions, the task's first session starts at or after the blocker's last session ends. A blocked task has no sessions to compare.

Re-planning uses the same capture, repair, and placement against the shrunk window.

### Warning

The summary flag `hasWarning` stays true when any inherited must-include task has an unplaced row, which now includes `BLOCKED`.

`DailyPlanWarning` gains `blockedTasks`: `{ sourceTaskId, title, blockerSourceTaskIds }[]`, built from the revision snapshot. A warning is present when any of the out-of-time, unestimated, or blocked lists is non-empty. Blocked minutes stay in `requiredMinutes` and are listed on their own, so they are not also described as time the day could not fit.

### Concurrency

Dependency writes take the owner scheduling lock for the cycle check and the insert or delete.

Generate saves the captured link snapshot even if the live links change during the provider call. It does not return `PLAN_CHANGED` and it does not set `needsRefresh` for that drift. `needsRefresh` remains the 1.3.0 effort and plannability check.

Re-plan persistence rechecks the captured link set under the owner lock, alongside the existing revision id and effort versions. A mismatch returns **409** `PLAN_CHANGED` and leaves the previous revision actionable.

## Task UI

The task form lists `blockedBy` and can add or remove one blocker at a time. A cycle, duplicate, or self-link is shown on that action. The add control lists the owner's other tasks.

The task list shows two counts taken from active blockers and active dependents only: "Blocked by N" and "Blocks N". Finished links stay visible on the form and do not inflate the counts.

An inherited must-include task whose own status and due date would not have put it in that group shows "Needed for {title}". The named task is the plannable task in its blocking chain whose own group equals the inherited group. Ties prefer the earliest due date, then the lowest task id. A plan uses the revision snapshot for the chain. The task list uses the live links. The plan also shows that task's due date when it has one.

Unplaced `BLOCKED` rows say "Waiting on {blocker titles}" using the revision snapshot. The shortfall alert keeps its out-of-time and unestimated lists, and adds the blocked list with the same waiting-on copy.

The outcome dialog names active blockers and still saves.

## Working Weekdays

Scheduling preferences gain the seven weekdays. At least one must be selected. The in-code default, and the backfill for saved preference rows, is Monday through Friday. Users who have never saved preferences receive that default from the effective read.

`GET` and `PUT /api/scheduling-preferences` include `workingDays`, the selected `DayOfWeek` values. An empty set, a duplicate, or an unknown value is an ordinary **400**.

The settings form shows seven toggles and states that the set shapes the horizon. Generating a Daily plan for a date stays available on every date, including dates outside the set.

## Horizon

### Read

`GET /api/horizon?currentDate={date}&currentTime={time}` returns **200** for the current owner. Both parameters are required. `currentTime` is minute-aligned. The server does not substitute its own clock. A missing or unaligned value is an ordinary **400**. A `currentDate` later than any saved plan is accepted and starts the span there.

The read takes no owner lock, calls no provider, and writes nothing. It is not subject to `PLAN_CANDIDATE_LIMIT`. An owner with no plannable tasks and no saved plans in range gets the day columns and an empty task list.

The pure forecast lives in `com.focusflow.horizon`, with the same ArchUnit boundary as `com.focusflow.schedule`. `HorizonController` and `HorizonService` live in the plan feature and load tasks, links, preferences, commitments, and saved plans through the existing facades.

### Columns

Walk forward from `currentDate` inclusive and take seven dates whose weekday is a working day. The span ends on that seventh working day. Columns are every date from `currentDate` through that end date which is either a working day or a non-working day that already has a Daily plan, in calendar order. A non-working day with a saved plan is an extra column. It does not consume one of the seven.

### Saved days

A date that has a Daily plan is a saved column. Today shows each task's work minutes on the composed rail from 1.3.0. Any other saved date shows the latest revision. Unplaced rows from that same rail or revision are included. The column carries the plan id and the plan's existing `needsRefresh` flag.

Displayed minutes are the saved plan's minutes. They are not rewritten when links or effort change later.

`dependenciesIgnored` lists the source task ids that have a displayed work session on that saved day while a live active blocker is not satisfied before that session. An active blocker with unknown remaining effort is never satisfied. An active blocker with known remaining effort is satisfied when assumed completion on earlier horizon days, plus displayed sessions of the blocker on this day that end at or before the dependent's first session, accounts for that whole remainder. The column copy states that the saved plan was made without the current dependency, that generating again applies it, and that this plan is left as saved. This flag does not set `needsRefresh`.

### As-planned carry

Each plannable task starts from its live remaining effort. Unknown effort stays unknown and is never reduced by a session length.

Walking saved columns in order, and sessions in start-time order, an unrecorded work session of a still-plannable task consumes `min(planned minutes, running remainder)`. Sessions that already have an outcome or a reconciliation marker consume nothing, because the live remainder already includes their credit. No-longer-needed sessions consume nothing. The running remainder never goes below zero.

That is the whole pace model. Elapsed unrecorded sessions are included, so a saved morning still counts until the user records skipped or partly done work. The horizon page says this in one sentence: unrecorded sessions on saved plans are assumed to be completed as planned, and recording skipped or partly done work updates the rest of the horizon.

### Forecast days

A column with no Daily plan is forecast. Its input for each plannable task is the running remainder at that date. A task whose running remainder is zero is omitted. Unknown remainder stays unknown.

Today, when it has no saved plan, is forecast from `currentTime` through the work-window end. A `currentTime` before the window start is clamped to the window start. A `currentTime` at or after the window end places nothing that day and leaves the remainder for later columns. The horizon request itself still succeeds.

Later forecast days use the full current work window. Commitments are loaded for that date. Cadence, minimum session, trailing buffer, and fixed breaks come from the owner's current effective preferences. Peak hours are not drawn, because the horizon is day-grained.

Ordering for a forecast day is fixed:

1. A task that already has assumed or forecast placed minutes on an earlier column is treated as must-continue, together with live In-progress tasks.
2. Inherited urgency groups, from the live links and live due dates, in group order.
3. Inside a group: earliest inherited due date, then `HIGH`, `MEDIUM`, `LOW`, then ascending task id. The inherited due date is the earliest due date among the task and the plannable tasks it blocks. A chain with no due date sorts after dated work.
4. The same stable dependency repair used for daily planning.

The existing two-stage scheduler places that order, including `BLOCKED`. Placed minutes then reduce that task's running remainder. `BLOCKED` and `NO_ESTIMATE` reduce nothing, and an `OUT_OF_TIME` remainder stays in the running total. Forecast placement does not create a Daily plan, a revision, or a task snapshot.

A forecast column's header says it uses this fixed order, and that generating a Daily plan for the date can choose a different order inside the same groups. The link target is `/dashboard?date={date}`.

### Deadline status

Each horizon row that is still plannable and has a due date gets one status. Precedence is top to bottom:

| Status | When |
|---|---|
| `OVERDUE` | The due date is before `currentDate`. |
| `CANNOT_FORECAST` | Remaining effort is unknown, or an active blocker chain includes a task with unknown remaining effort. |
| `ON_TRACK` | A column on or before the due date leaves the running remainder at zero. |
| `AT_RISK` | The due date falls inside the span, and the running remainder is still positive after every column on or before that due date. |
| `BEYOND_HORIZON` | The due date is after the last column, and the remainder is still positive at the end of the span. |

A task with no due date has a null status. A Done or Cancelled task included only because a saved plan shows it also has a null status.

`AT_RISK` and `CANNOT_FORECAST` include `waitingOn`: the active blockers that are themselves unfinished inside the horizon, as `{ taskId, title }`. An overdue task may include the same list. The list is empty when the due date is missed only because the day ran out of time.

The projected finish date is the last column on which the task has placed minutes and after which its running remainder is zero. It is null when the remainder never reaches zero.

### Response

```text
currentDate, currentTime
assumptions: { pace: "AS_PLANNED", workingDays, horizonWorkingDays: 7 }
days: [{ date, kind: SAVED | FORECAST, planId | null, needsRefresh, dependenciesIgnored }]
tasks: [{
  taskId, title, status, dueDate, remainingEffortMinutes,
  deadlineStatus, projectedFinishDate, waitingOn,
  segments: [{ date, minutes, unplacedReason | null, unplacedMinutes | null }]
}]
```

`minutes` is the placed work for that task on that date. `unplacedReason` is set when that date left a remainder, and it may appear beside positive minutes for `OUT_OF_TIME`. `unplacedMinutes` is the remainder left that day, and it is null for `NO_ESTIMATE` and for a blocked task whose remaining effort is unknown. `BLOCKED` and `NO_ESTIMATE` have zero placed minutes. A task with neither minutes nor an unplaced reason on a date omits that date.

Rows are the union of plannable tasks that appear on at least one date and tasks that appear only because a saved plan displays them. Row order is the deterministic forecast order computed for the first working day in the span, whether or not that day is saved. Tasks that appear only because a saved plan displays them follow, ordered by title, then task id.

### Gantt

The horizon is a new `/horizon` page, linked from the sidebar between Plans and Settings. It is a CSS grid: one sticky title column, one column per horizon day, one row per task. A cell's bar is proportional to that day's placed minutes against the work-window length, so days can be compared. Saved headers and forecast headers are visually distinct. A due date that is one of the columns gets a marker on that column.

`BLOCKED`, `NO_ESTIMATE`, and `OUT_OF_TIME` are text in the cell. `OUT_OF_TIME` can sit next to a partial bar. Waiting-on relationships are the `waitingOn` text and a hover state on the blocker row. The page does not draw dependency arrows.

Each segment is keyboard-focusable and its accessible name includes the task title, date, minutes, and whether the day is saved or forecast. The grid scrolls horizontally. The title column stays sticky.

The task list reads the same horizon query. It shows "At risk" for `AT_RISK` and "Overdue" for `OVERDUE`. Other statuses add no badge.

There is no chart library and no drag handling.

### Cache

The horizon query key includes `currentDate`. Task edits, dependency changes, preference saves, commitment changes, progress saves, unplanned-work changes, generate, and re-plan invalidate it along with the plan and task queries they already invalidate.

## Schema And Migration

The next forward-only Flyway migration after `V6__done_task_zero_remaining.sql` is `V7`. It deletes nothing.

It adds:

- `task_dependencies`: owner, blocked task, blocker task, a uniqueness constraint on the pair, and a check that the two task ids differ. Both task foreign keys cascade on delete.
- `daily_plan_revision_dependencies`: revision id plus the two source task ids, cascading with the revision. These rows do not reference the live task table.
- Seven non-null boolean weekday columns on `scheduling_preferences`. Existing rows are backfilled to Monday through Friday.

Existing Daily plans gain no dependency rows. Readers treat a missing snapshot as an empty link set.

## Upgrade

Existing tasks have no links, so generate, re-plan, and the horizon behave as they do today until the owner adds one. Existing preference rows become Monday through Friday, which affects only the new horizon. Existing plans remain readable, keep their stored `mustInclude` bits, and can still be re-planned under the 1.3.0 rules. A re-plan after this migration captures the live links, which are empty until the owner creates one.

## Acceptance Scenarios

- Adding a blocker that is the same task returns `SELF_DEPENDENCY` and stores nothing. Adding the same pair twice returns `DEPENDENCY_EXISTS` on the second add. Adding a pair that closes a chain, including a chain through a Done task, returns `DEPENDENCY_CYCLE`. Two concurrent adds that would form a cycle result in one success and one `DEPENDENCY_CYCLE`.
- B is Open and due today. A is Open with no due date and blocks B. Generation labels both as due-or-overdue, places A before B, and stores `mustInclude` on both. The task list shows "Needed for B" on A. Deleting the link and generating again leaves A optional.
- The model returns a valid block order with B before A inside that due group. The saved rank and the clock both have A before B. No **502** is returned for that inversion.
- The model places an optional task before a must-continue task. Validation still fails with **502** and saves nothing.
- A has unknown remaining effort and blocks B, which has a known estimate. Both are unplaced, A as `NO_ESTIMATE` and B as `BLOCKED`, and B has no work session in the gap A skipped. The unplaced row says it is waiting on A.
- A fits fully, and B does not fit after it. B is `OUT_OF_TIME`, not `BLOCKED`, and B's first session starts at or after A's last session ends.
- A is only partly placed. B is `BLOCKED` for its full remaining effort, with no session before A.
- A must-include blocker that does not fit appears in the out-of-time warning. The task it blocks appears in `blockedTasks` and not in the out-of-time list. `requiredMinutes` includes both known remainders. A plan whose only must-include gap is `BLOCKED` still sets `hasWarning`.
- Finishing A, or cancelling A, lets the next generation place B. The link remains. Reopening A with a fresh remainder makes the next generation block B again. Recording B partly done while A is still active saves the outcome.
- A revision's dependency snapshot still explains a `BLOCKED` row after the live link is removed. The plan does not show `needsRefresh` because of that removal. A migrated revision has no dependency snapshot and no blocked explanation.
- A re-plan whose links change while the provider call is in flight returns `PLAN_CHANGED` and keeps the previous revision. A generate in the same race saves the captured links and does not set `needsRefresh`.
- The default horizon is the next seven Monday-through-Friday dates. Saturday appears only when it has a saved plan, and that column does not replace a working day. Clearing every weekday is rejected. Generating a plan for Saturday still succeeds.
- Today's saved plan has an unrecorded 50-minute session and the live remainder is 80. The next forecast day places the other 30. After the user marks that session skipped, the next forecast day places 80. A done session is not subtracted a second time.
- Tomorrow's saved plan still displays its own sessions after today's assumption would already have finished the task. The following forecast day places nothing for it. The tomorrow column shows `needsRefresh` only when the 1.3.0 rule already would.
- A saved plan schedules B before live blocker A has finished. That column lists B in `dependenciesIgnored` and does not change the plan.
- A task due inside the span whose remainder reaches zero on time is `ON_TRACK`. The same shape finishing after the due date is `AT_RISK`. A due date before `currentDate` is `OVERDUE` even when the effort is unknown. Unknown effort with a future due date is `CANNOT_FORECAST`. A due date after the span, with work left, is `BEYOND_HORIZON`. `AT_RISK` caused by an unfinished blocker names that blocker.
- Today with no plan, requested after the work window has ended, contributes an empty forecast column and places the remainder on the next working day.
- The horizon with no plannable tasks and no saved plans in the span returns **200**, the day columns, and an empty task list, and it does not call the provider.

## Suggested Decomposition

This spec is one milestone. A later implementation plan can split it without changing the product rules:

1. Dependency storage, cycle checks, task API, and task UI.
2. Inherited urgency, prompt labels, repair, `BLOCKED` placement, revision snapshots, and warning copy.
3. Working weekdays on preferences.
4. The pure horizon forecast and `GET /api/horizon`.
5. The Gantt page, deadline badges, and cache invalidation.
