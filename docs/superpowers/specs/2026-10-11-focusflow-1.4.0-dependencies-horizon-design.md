Date: 2026-10-11

## Purpose

1.3.0 plans one day, records progress, and carries unfinished remaining effort into the next day the user generates. It cannot say that one task has to finish before another, and it cannot show whether a later due date will be missed.

1.4.0 adds finish-to-start dependencies to daily planning, then a read-only seven-working-day horizon that reuses the existing scheduler. The horizon is calculated when it is viewed. Daily plans remain the only saved schedules.

This is a design document, not an implementation plan. It assumes 1.3.0 is already built: remaining effort, schedule revisions, the composed day rail, and revision-preserving re-planning.

The work is one milestone in two slices. Dependencies can ship before the horizon. The horizon consumes the dependency rules and is not a second product.

## Goals And Non-Goals

Goals:

- Let the owner link tasks with finish-to-start dependencies, reject self-links, duplicates, and cycles, and show the links on the task form and task list.
- Treat Done and Cancelled blockers as released while keeping the link. Reopening the blocker makes it block again.
- Give a blocker the urgency of the plannable work waiting on it, so must-include order and dependency order agree.
- Ask the model for that inherited order, then repair remaining dependency inversions in Java before placement.
- Leave a task unplaced as `BLOCKED` when an active blocker in the same ranking is not fully placed, including a blocker with unknown remaining effort.
- Snapshot the dependency links used for a revision, and explain blocked and inherited work from that snapshot.
- Add working weekdays to scheduling preferences, defaulting to Monday through Friday, and use them only for the horizon.
- Show the next seven working days as a horizontal Gantt. Saved daily plans occupy their dates. Other working days are a fixed-rule forecast.
- Assume eligible unrecorded sessions on saved plans are completed as planned, and forecast each later day from the effort that assumption leaves. A session that violates a current dependency, or that falls on or before a remaining-effort checkpoint its revision did not capture, does not count.
- Report whether due work is on track, at risk, overdue, beyond the horizon, or impossible to forecast.

Non-goals:

- No persisted multi-day plan, no saved horizon snapshot, and no separate "re-plan the week" command. Refreshing the horizon is another read.
- No horizon start-date picker and no reconstruction of past task state. The forecast starts from the client's current date and time.
- No AI call for the horizon, and no per-day provider ranking.
- No history-based pace. The forecast assumes work is done as planned.
- No change to daily-plan generation on non-working days. Working weekdays do not reject a generate.
- No start-to-start, finish-to-finish, or lead/lag dependencies. One link means finish-to-start.
- No subtasks, recurring tasks, or rolled-up parent estimates.
- No drag-to-reschedule, manual block editing, or a chart library.
- No refusal of progress on a blocked task. The schedule waits; the outcome dialog does not.
- No expansion of `needsRefresh` to cover dependency edits. A saved plan keeps the links it captured.
- No change to cadence, minimum session, fixed breaks, commitments, trailing buffer, the hard window end, or peak-window display.
- No new authentication, CSRF, or Flyway-policy design. New conflicts use the existing coded-error contract.

## Domain Language

Terms below amend `CONTEXT.md`. Prefer the glossary when it disagrees with older specs.

**Task dependency**:
A finish-to-start link from a blocker to a blocked task. The blocked task may be scheduled only after the blocker's planned completion. A Done or Cancelled blocker releases the blocked task, and the link stays.
_Avoid:_ Subtask, parent task

**Active dependency**:
A task dependency whose blocker and blocked task are both plannable. Only an active dependency counts as "Blocked by" or "Blocks" and constrains a new schedule.

**Active blocker**:
A blocker whose live status is Open or In progress. A Done or Cancelled blocker releases the blocked task. The link stays.

**Planned completion**:
A blocker whose known remaining effort is fully placed in a schedule, with nothing left unplaced. It permits the blocked task to be scheduled and does not by itself mark the blocker Done.

**Inherited urgency**:
The ranking group a task receives from its own status and due date and from plannable tasks reached through Open or In-progress tasks. A Done or Cancelled task stops that chain. A blocker is at least as urgent as the work waiting on it.

**Blocked work**:
A plannable task left entirely unplaced because an active blocker in the same ranking was not fully placed.
_Avoid:_ Out of time, no estimate

**Working day**:
A weekday the owner includes in the horizon. It does not limit which dates can have a Daily plan.

**Horizon**:
The read-only forecast of the next seven working days, calculated from live tasks, current preferences, commitments, and saved Daily plans.
_Avoid:_ Multi-day plan, weekly plan

**Forecast day**:
A horizon day that has no Daily plan. Its placement uses fixed ordering rules and the existing scheduler.

**As-planned pace**:
The horizon assumption that an eligible unrecorded work session on a saved Daily plan is completed as planned.
_Avoid:_ Actual minutes, history-based pace

**Assumed credit**:
The planned minutes of an eligible unrecorded work session that the horizon counts toward completion, up to the task's live remaining effort. A session receives none when it starts before an active blocker is satisfied, or when its date is on or before a later remaining-effort checkpoint that its schedule revision did not capture.

## Dependencies

### Links

A dependency row belongs to the owner and names two of that owner's tasks: the blocker and the blocked task. The pair is unique. A task may block many tasks and may be blocked by many tasks. Deleting a task deletes every link in which it appears. Links are not copied onto the surviving task snapshots except through the revision snapshot defined below.

Cycle detection uses every link the owner has, including links whose blocker is Done or Cancelled. A cycle that is hidden by a finished task would reappear when that task is reopened. The check runs while the owner row is locked, together with the insert or delete, so two concurrent adds cannot each store one half of a cycle.

An active blocker is Open or In progress. Done and Cancelled blockers do not constrain ranking or placement. Finishing or cancelling a blocker releases its dependents on the next generate, re-plan, or horizon read. Reopening it to Open or In progress, which already requires a fresh remaining-effort assessment, makes the link active again.

Recording progress, unplanned work, or a checkpoint against a blocked task stays legal. The outcome dialog names the active blockers and still saves.

Adding or removing a link does not change `effortVersion` and does not mark any Daily plan as needing refresh.

### Urgency inheritance

Ranking groups stay the three groups from 1.0.2:

1. Must-continue: In progress.
2. Due/overdue: Open, with a due date on or before the planning date.
3. Optional: every other plannable task.

A task's inherited group is the most urgent group among itself and every plannable task reachable by following "blocks" links through Open or In-progress tasks. A Done or Cancelled task stops the chain. Done and Cancelled dependents do not grant urgency. The task's stored status and due date stay unchanged. `mustInclude` on a new revision is true for inherited groups 1 and 2. The inherited due date and the "Needed for" task use this same active chain.

This is what keeps dependency order inside the existing block order. If B is due today and A blocks B, A inherits group 2 even when A has no due date. A then ranks with due work, before optional work, and the dependency rule can still put A before B. Without inheritance those two rules contradict each other, and the collision the roadmap left open is resolved in favor of the blocker.

`requiredMinutes` remains the sum of known remaining effort on inherited must-include tasks, including must-include tasks that end up blocked.

### API

All mutating dependency operations use the existing session and CSRF rules. Unknown or other-owner task ids return **404**.

| Method and path | Body | Success |
|---|---|---|
| `POST /api/tasks/{id}/blockers` | `{ "blockerTaskId": number }` | **200** `TaskResponse` |
| `DELETE /api/tasks/{id}/blockers/{blockerId}` | — | **204** |

`TaskResponse` gains:

- `blockedBy`: `{ taskId, title, status }[]`
- `blocks`: `{ taskId, title, status }[]`

Both lists include finished tasks so the form can show and remove a link that is not currently blocking. List and get both return them.

New codes:

| Code | Status | When |
|---|---|---|
| `SELF_DEPENDENCY` | **400** | `blockerTaskId` is the same task. |
| `DEPENDENCY_EXISTS` | **409** | That pair is already stored. |
| `DEPENDENCY_CYCLE` | **409** | The new link would make a task reachable from itself. |

A delete of a link that is not present is **404**. Validation failures that only restate a missing field stay ordinary client errors.

### Pure dependency package

`com.focusflow.dependency` holds the cycle check, inherited-group assignment, and stable reorder. It accepts plain values, not JPA entities or HTTP DTOs, and it does not call Spring. ArchUnit protects it the same way it protects `com.focusflow.schedule` and `com.focusflow.effort`.

`TaskQueryService` is the read facade for an owner's links. The plan feature does not touch the task dependency repository.

## Daily Planning

### Capture

Generate and re-plan load the owner's links with the plannable candidates, before the provider call. Inherited groups, the prompt, ranking validation, the repaired order, placement, `mustInclude`, and the revision's dependency snapshot all use that captured set.

The persisted rank is the repaired order, because that is the order placement walks. The raw model order is not stored.

The revision snapshot stores one row per captured direct link whose blocker and blocked task are both in that revision's candidate set. Later link edits do not rewrite it. A revision migrated from earlier milestones has no dependency rows, which means it was planned with no dependencies.

### Prompt and validation

Each candidate line gains two fields computed from the captured links:

- `block=must-continue`, `block=due-or-overdue`, or `block=optional`, using the inherited group.
- `blockedBy=` followed by the captured active blocker ids that are in the candidate set.

The ranking rules tell the model to use the labeled block rather than recompute it from status and due date, and to place a task after every id in its `blockedBy` list.

`DailyPlanRankingValidator` classifies candidates with those same inherited groups. It still rejects unknown ids, duplicates, missing candidates, and block-order violations. It does not reject a dependency inversion. Intra-group order remains the model's choice except for the repair below.

### Repair

After validation succeeds, Java produces a new permutation. Repeatedly take the not-yet-emitted candidate with the earliest original index whose captured active blockers in the candidate set are already emitted. The result is the placement order.

Because every active blocker inherits a group at least as urgent as the tasks it blocks, a block-ordered input can be repaired without moving a later group ahead of an earlier group. If a repair would do that anyway, planning fails as an invalid ranking: **502**, and nothing is saved. That failure is a broken invariant, not a user-correctable conflict.

Rejecting the model outright for a dependency inversion was considered and rejected. Dependency order is a hard constraint Java can apply without guessing, and a rejection would turn an intra-group mistake into a provider failure. Block-order violations are still rejected, as they are today. See ADR 0029.

### Placement

`WorkPlacementPlanner` gains the captured direct links among the ranked tasks. Before placing a task it looks at each active blocker that is also in the ranking:

- When every such blocker is fully placed, placement is unchanged. Fully placed means the blocker's scheduled minutes equal its known remaining effort and it has no unplaced row. That is planned completion for this schedule. It does not change the blocker's live status.
- Otherwise the task is blocked. It gets no work blocks. It gets one unplaced row with reason `BLOCKED`. Known remaining effort is stored in full as the unplaced minutes. Unknown remaining effort stores null minutes.

`BLOCKED` wins over `NO_ESTIMATE`. A blocked task with unknown effort is `BLOCKED`, not `NO_ESTIMATE`. A task is never partly blocked: either its blockers are fully placed and ordinary placement may still leave an `OUT_OF_TIME` remainder, or the task contributes no sessions at all. A gap before an unfinished blocker is not available to the blocked task.

An unestimated blocker is not fully placed, because it has a `NO_ESTIMATE` row and no sessions. Tasks it blocks therefore stay `BLOCKED` instead of sliding into the time the blocker skipped. That is the scheduler change this milestone requires. The cursor-only behavior would schedule them.

The postcondition validator gains two conservation cases and one order check:

- Known remaining effort and `BLOCKED`: exactly one `BLOCKED` row, unplaced minutes equal to that effort, and no work blocks.
- Unknown remaining effort and `BLOCKED`: exactly one `BLOCKED` row with null minutes, and no work blocks.
- Unknown remaining effort and not blocked: the existing single `NO_ESTIMATE` row.
- Known remaining effort and not blocked: the existing rule, scheduled minutes plus `OUT_OF_TIME` minutes equals the captured remaining effort.
- When both a task and its captured active blocker have work sessions, the task's first session starts at or after the blocker's last session ends. A blocked task has no sessions to compare.

Re-planning uses the same capture, repair, and placement against the shrunk window.

### Warning

The summary flag `hasWarning` stays true when any inherited must-include task has an unplaced row, which now includes `BLOCKED`. Optional blocked work does not set it.

`DailyPlanWarning` gains `blockedTasks`: `{ sourceTaskId, title, blockerSourceTaskIds }[]`, built from the revision snapshot and limited to inherited must-include tasks. A warning is present when any of those must-include out-of-time, unestimated, or blocked lists is non-empty. Blocked minutes stay in `requiredMinutes` and are listed on their own, so they are not also described as time the day could not fit. An optional blocked task still has its own "Waiting on" unplaced row.

### Concurrency

Dependency writes take the owner scheduling lock for the cycle check and the insert or delete.

Generate saves the captured link snapshot and each candidate's captured checkpoint id even if the live links or checkpoints change during the provider call. It does not return `PLAN_CHANGED` and it does not set `needsRefresh` for link drift. `needsRefresh` remains the 1.3.0 effort and plannability check. A revision that captured an older checkpoint keeps that id when a newer checkpoint arrives during the call.

Re-plan persistence rechecks the captured active links among the captured candidates under the owner lock, alongside the existing revision id and effort versions. A link counts only when both tasks are in that candidate set and the blocker is Open or In progress. A change outside that set, such as a link between two finished tasks, does not by itself return `PLAN_CHANGED`. A mismatch in the compared set returns **409** `PLAN_CHANGED` and leaves the previous revision actionable.

## Task UI

The task form lists `blockedBy` and can add or remove one blocker at a time. A cycle, duplicate, or self-link is shown on that action. The add control lists the owner's other tasks.

The task list shows two counts taken from active dependencies only: "Blocked by N" and "Blocks N". Both tasks must be Open or In progress. A finished task does not show a count for a retained link to a plannable neighbor. Finished links stay visible on the form and do not inflate the counts.

An inherited must-include task whose own status and due date would not have put it in that group shows "Needed for {title}". The named task is the plannable task in its active blocking chain whose own group equals the inherited group. Ties prefer the earliest due date, then the lowest task id. A plan uses the revision snapshot for the chain. The task list uses the live links. The plan also shows that task's due date when it has one.

Unplaced `BLOCKED` rows say "Waiting on {blocker titles}" using the revision snapshot. The shortfall alert keeps its out-of-time and unestimated lists, and adds the blocked list with the same waiting-on copy.

The outcome dialog names active blockers and still saves.

## Working Weekdays

Scheduling preferences gain the seven weekdays. At least one must be selected. The in-code default, and the backfill for saved preference rows, is Monday through Friday. Users who have never saved preferences receive that default from the effective read.

`GET` and `PUT /api/scheduling-preferences` include `workingDays`, the selected `DayOfWeek` values. An empty set, a duplicate, or an unknown value is an ordinary **400**.

The settings form shows seven toggles and states that the set shapes the horizon. Generating a Daily plan for a date stays available on every date, including dates outside the set.

## Horizon

### Read

`GET /api/horizon?currentDate={date}&currentTime={time}` returns **200** for the current owner. Both parameters are required. `currentTime` is minute-aligned. The server does not substitute its own clock. A missing or unaligned value is an ordinary **400**. The horizon page always sends the client's current date and minute-aligned current time. It has no start-date picker. The server still forecasts from live task state, so another date is not a historical reconstruction.

The read takes no owner lock, calls no provider, and writes nothing. Tasks, checkpoints, links, preferences, commitments, and saved plans come from one read-only snapshot, so a progress save that commits during the read is entirely included or entirely excluded. It is not subject to `PLAN_CANDIDATE_LIMIT`. An owner with no plannable tasks and no saved plans in range gets the day columns and an empty task list.

The pure forecast lives in `com.focusflow.horizon`, with the same ArchUnit boundary as `com.focusflow.schedule`. `HorizonController` and `HorizonService` live in the plan feature and load tasks, links, checkpoints, preferences, commitments, and saved plans through the existing facades.

### Columns

Walk forward from `currentDate` inclusive and take seven dates whose weekday is a working day. The span ends on that seventh working day. Columns are every date from `currentDate` through that end date which is either a working day or a non-working day that already has a Daily plan, in calendar order. A non-working day with a saved plan is an extra column. It does not consume one of the seven.

### Saved days

A date that has a Daily plan is a saved column. Today shows each task's work minutes on the composed rail from 1.3.0. Any other saved date shows the latest revision. Unplaced rows from that same rail or revision are included. The column carries the plan id and the plan's existing `needsRefresh` flag.

Displayed minutes are the saved plan's minutes. They are not rewritten when links or effort change later. Saved unplaced minutes stay the revision's original shortfall and are labelled as that saved plan's shortfall. They are not described as the task's current remaining effort.

`dependenciesIgnored` lists the source task ids that have at least one displayed work session on that saved day whose start is before a live active blocker is satisfied. Satisfaction is judged per session. An active blocker with unknown remaining effort is never satisfied. An active blocker with known remaining effort is satisfied for a session when assumed credit on earlier horizon days, plus this day's displayed sessions of the blocker that end at or before that session starts, accounts for the blocker's whole live remainder. The column copy states that a saved session conflicts with a current dependency, that generating again applies the current rules, and that this plan is left as saved. It does not say whether the dependency was added after the plan. This flag does not set `needsRefresh`.

### As-planned carry

Each plannable task starts from its live remaining effort. Unknown effort stays unknown and is never reduced by a session length.

Walking saved columns in order, and sessions in start-time order, an unrecorded work session of a still-plannable task receives assumed credit of `min(planned minutes, running remainder)` only when the session is eligible. Sessions that already have an outcome or a reconciliation marker consume nothing, because the live remainder already includes their credit. No-longer-needed sessions consume nothing. The running remainder never goes below zero.

A session is eligible when both are true:

- Every live active blocker is satisfied before it starts, using the per-session rule above. A later session on the same saved day can count after an earlier session for that task does not.
- The task has no remaining-effort checkpoint, or its plan date is after that checkpoint's work date, or its plan date is that work date and the session's schedule revision captured that checkpoint. Sessions on or before the checkpoint date otherwise count as already covered by the assessment. A revision qualifies for this same-day exception only when the checkpoint id stored on its task snapshot equals the task's latest checkpoint id. The revision's save time is not the test. A generation that captured an older assessment and saved after the checkpoint does not qualify.

Each new daily-plan task stores that captured checkpoint id. There is no foreign key: equal remaining minutes do not identify which assessment was used, and detaching the checkpoint must not erase the evidence. Null means no checkpoint was captured. A migrated revision has null and does not receive the same-day exception.

That is the whole pace model. Elapsed unrecorded sessions are included when they are eligible, so a saved morning still counts until the user records skipped or partly done work or a later assessment covers it. The horizon page says this in one sentence: eligible unrecorded sessions on saved plans are assumed completed as planned, while a dependency conflict or an assessment that already covers the session is excluded, and recording skipped or partly done work updates the rest of the horizon.

### Forecast days

A column with no Daily plan is forecast. Its input for each plannable task is the running remainder at that date. A task whose running remainder is zero is not offered to that day's scheduler. Unknown remainder stays unknown. The task still keeps its horizon row.

Today, when it has no saved plan, is forecast from `currentTime` through the work-window end. A `currentTime` before the window start is clamped to the window start. A `currentTime` at or after the window end places nothing that day and leaves the remainder for later columns. The horizon request itself still succeeds.

Later forecast days use the full current work window. Commitments are loaded for that date. Cadence, minimum session, trailing buffer, and fixed breaks come from the owner's current effective preferences. Peak hours are not drawn, because the horizon is day-grained.

Ordering for a forecast day is fixed:

1. Mark live In-progress tasks, and tasks that already have assumed credit or forecast placed minutes on an earlier column, as must-continue.
2. Inherited urgency through active chains, including that forecast must-continue group, so an unfinished blocker is at least as urgent as the work waiting on it. Groups stay in must-continue, due/overdue, then optional order.
3. Inside a group: earliest inherited due date, then `HIGH`, `MEDIUM`, `LOW`, then ascending task id. The inherited due date is the earliest due date among the task and the plannable tasks reached through its active chain. A chain with no due date sorts after dated work.
4. The same stable dependency repair used for daily planning. Inheritance keeps that repair inside group order. A repair that would move a later group ahead of an earlier one is a broken invariant: the read fails with **500** and returns no partial forecast.

The existing two-stage scheduler places that order, including `BLOCKED`. Placed minutes then reduce that task's running remainder. `BLOCKED` and `NO_ESTIMATE` reduce nothing, and an `OUT_OF_TIME` remainder stays in the running total. Forecast placement does not create a Daily plan, a revision, or a task snapshot.

A forecast column's header says it uses this fixed order, and that generating a Daily plan for the date can choose a different order inside the same groups. The link target is `/dashboard?date={date}`.

### Deadline status

Each horizon row that is still plannable and has a due date gets one status. Precedence is top to bottom:

| Status | When |
|---|---|
| `OVERDUE` | The due date is before `currentDate`. |
| `CANNOT_FORECAST` | Remaining effort is unknown, or the active blocker chain includes a task with unknown remaining effort. A Done or Cancelled task stops that chain. |
| `ON_TRACK` | A column on or before the due date leaves the running remainder at zero. |
| `AT_RISK` | The due date falls inside the span, and the running remainder is still positive after every column on or before that due date. |
| `BEYOND_HORIZON` | The due date is after the last column, and the remainder is still positive at the end of the span. |

A task with no due date has a null status. A Done or Cancelled task included only because a saved plan shows it also has a null status.

The deadline reference is the due date when that date is on or before the last column, and the last column when the due date is later. A blocker is unfinished at a reference inside the span when its running remainder is still positive after every column on or before that date. A reference before `currentDate` has no such column, so every direct active blocker counts as unfinished then.

`AT_RISK`, `CANNOT_FORECAST`, and `OVERDUE` may include:

- `waitingOn`: the direct active blockers unfinished at the deadline reference, as `{ taskId, title }`. The list is empty when the due date is missed only because the day ran out of time.
- `upstreamBlockers`: other plannable tasks farther up that active chain which are unfinished at the same reference or have unknown remaining effort. Direct blockers are not repeated here.
- `unresolvedEffort`: every task in that chain, including the row's own task, whose remaining effort is unknown.

A blocker that finishes inside the horizon but after the due date is still named. `BEYOND_HORIZON` uses the same lists at the horizon end. `ON_TRACK` leaves them empty.

The projected finish date is the first column on which credited work reduces the running remainder to zero. A later saved session that still displays minutes does not move it. It is null when the remainder never reaches zero.

### Response

```text
currentDate, currentTime
assumptions: { pace: "AS_PLANNED", workingDays, horizonWorkingDays: 7 }
days: [{ date, kind: SAVED | FORECAST, planId | null, needsRefresh, dependenciesIgnored }]
tasks: [{
  taskId, title, status, dueDate, remainingEffortMinutes,
  deadlineStatus, projectedFinishDate, waitingOn, upstreamBlockers, unresolvedEffort,
  segments: [{
    date, minutes, assumedCreditMinutes | null, creditExclusions,
    unplacedReason | null, unplacedMinutes | null, unplacedScope: SAVED_SHORTFALL | FORECAST | null
  }]
}]
```

`minutes` is the placed work displayed for that task on that date. On a saved segment, `assumedCreditMinutes` is the portion that counted toward the running remainder, and `creditExclusions` lists `DEPENDENCY`, `CHECKPOINT`, or both when some displayed minutes were excluded. A forecast segment has null assumed credit and an empty exclusion list; its placed minutes reduce the running remainder as forecast placement. `unplacedReason` is set when that date left a remainder, and it may appear beside positive minutes for `OUT_OF_TIME`. `unplacedMinutes` is the remainder recorded for that day. It is null for `NO_ESTIMATE` and for a blocked task whose remaining effort is unknown. On a saved segment those minutes are the revision's historical shortfall, `unplacedScope` is `SAVED_SHORTFALL`, and the cell says so. On a forecast segment `unplacedScope` is `FORECAST`. `BLOCKED` and `NO_ESTIMATE` have zero placed minutes. A task with neither minutes nor an unplaced reason on a date omits that date.

Rows are every plannable task, including one with no segments, plus tasks that appear only because a saved plan displays them. Row order is the deterministic forecast order computed for the first working day in the span, whether or not that day is saved. Tasks that appear only because a saved plan displays them follow, ordered by title, then task id.

### Gantt

The horizon is a new `/horizon` page, linked from the sidebar between Plans and Settings. It is a CSS grid: one sticky title column, one column per horizon day, one row per task. Bar length uses one scale for the whole span: displayed minutes divided by the longest full work window among the columns. A saved column contributes its captured window length, and a forecast column contributes the current work window. Equal minutes have equal bar lengths. Saved headers and forecast headers are visually distinct. The task title always shows the actual due date. A column marker appears only when that date is one of the columns.

`BLOCKED`, `NO_ESTIMATE`, and `OUT_OF_TIME` are text in the cell. `OUT_OF_TIME` can sit next to a partial bar. A saved shortfall is labelled as the saved plan's shortfall. When assumed credit differs from displayed minutes, the cell states both amounts and why minutes were excluded. Waiting-on relationships are the `waitingOn` text, the upstream cause when one exists, and a hover state on the blocker row. The page does not draw dependency arrows.

Each segment is keyboard-focusable and its accessible name includes the task title, date, displayed minutes, assumed credit when it differs, and whether the day is saved or forecast. The grid scrolls horizontally. The title column stays sticky.

The task list reads the same horizon query. It shows "At risk" for `AT_RISK`, "Overdue" for `OVERDUE`, and "Cannot forecast" for `CANNOT_FORECAST`. The last badge names the tasks in `unresolvedEffort`. Other statuses add no badge. If the horizon request fails, the task list and its actions still load. The badge area says "Deadline forecast unavailable" and offers retry. A missing badge is not presented as on track.

There is no chart library and no drag handling.

### Cache

The horizon query key includes `currentDate` and minute-aligned `currentTime`. While the horizon page is visible it advances that time each minute and refetches. It also refetches when the page becomes visible again. Task edits, dependency changes, preference saves, commitment changes, progress saves, unplanned-work changes, generate, and re-plan invalidate it along with the plan and task queries they already invalidate.

## Schema And Migration

The next forward-only Flyway migration after `V6__done_task_zero_remaining.sql` is `V7`. It deletes nothing.

It adds:

- `task_dependencies`: owner, blocked task, blocker task, a uniqueness constraint on the pair, and a check that the two task ids differ. Both task foreign keys cascade on delete.
- `daily_plan_revision_dependencies`: revision id plus the two source task ids, cascading with the revision. These rows do not reference the live task table.
- A nullable `captured_checkpoint_id` on each daily-plan task, with no foreign key. Existing rows stay null.
- Seven non-null boolean weekday columns on `scheduling_preferences`. Existing rows are backfilled to Monday through Friday.

Existing Daily plans gain no dependency rows. Readers treat a missing dependency snapshot as an empty link set and a null captured checkpoint id as no captured checkpoint.

## Upgrade

Existing tasks have no links, so generate, re-plan, and the horizon behave as they do today until the owner adds one. Existing preference rows become Monday through Friday, which affects only the new horizon. Existing plans remain readable, keep their stored `mustInclude` bits, and can still be re-planned under the 1.3.0 rules. A re-plan after this migration captures the live links, which are empty until the owner creates one, and stores the checkpoint id current at that capture. Migrated revisions keep a null checkpoint id.

## Acceptance Scenarios

- Adding a blocker that is the same task returns `SELF_DEPENDENCY` and stores nothing. Adding the same pair twice returns `DEPENDENCY_EXISTS` on the second add. Adding a pair that closes a chain, including a chain through a Done task, returns `DEPENDENCY_CYCLE`. Two concurrent adds that would form a cycle result in one success and one `DEPENDENCY_CYCLE`.
- B is Open and due today. A is Open with no due date and blocks B. Generation labels both as due-or-overdue, places A before B, and stores `mustInclude` on both. The task list shows "Needed for B" on A. Deleting the link and generating again leaves A optional.
- A is Open with no due date and blocks B. B is Done and its retained link blocks C, which is Open and due today. A does not inherit C's urgency and does not show "Needed for C". Adding a link that closes a cycle through B still returns `DEPENDENCY_CYCLE`. A's task-list count does not include B.
- The model returns a valid block order with B before A inside that due group. The saved rank and the clock both have A before B. No **502** is returned for that inversion.
- The model places an optional task before a must-continue task. Validation still fails with **502** and saves nothing.
- A has unknown remaining effort and blocks B, which has a known estimate. Both are unplaced, A as `NO_ESTIMATE` and B as `BLOCKED`, and B has no work session in the gap A skipped. The unplaced row says it is waiting on A.
- A fits fully, and B does not fit after it. B is `OUT_OF_TIME`, not `BLOCKED`, and B's first session starts at or after A's last session ends.
- A is only partly placed. B is `BLOCKED` for its full remaining effort, with no session before A.
- A must-include blocker that does not fit appears in the out-of-time warning. The task it blocks appears in `blockedTasks` and not in the out-of-time list. `requiredMinutes` includes both known remainders. A plan whose only must-include gap is `BLOCKED` still sets `hasWarning`. An optional task left `BLOCKED` keeps its waiting-on row and does not set `hasWarning`.
- Finishing A, or cancelling A, lets the next generation place B. The link remains. Reopening A with a fresh remainder makes the next generation block B again. Recording B partly done while A is still active saves the outcome.
- A revision's dependency snapshot still explains a `BLOCKED` row after the live link is removed. The plan does not show `needsRefresh` because of that removal. A migrated revision has no dependency snapshot and no blocked explanation.
- A re-plan whose active links among its captured candidates change while the provider call is in flight returns `PLAN_CHANGED` and keeps the previous revision. Removing a link between two finished tasks does not. A generate in the same race saves the captured links and checkpoint ids and does not set `needsRefresh` for that link drift.
- The default horizon is the next seven Monday-through-Friday dates. Saturday appears only when it has a saved plan, and that column does not replace a working day. Clearing every weekday is rejected. Generating a plan for Saturday still succeeds.
- Today's saved plan has an unrecorded 50-minute session and the live remainder is 80. No checkpoint or dependency excludes it. The next forecast day places the other 30. After the user marks that session skipped, the next forecast day places 80. A done session is not subtracted a second time.
- The same 50-minute session belongs to a revision that did not capture today's checkpoint of 90. The next forecast day places 90. A new revision that captured that checkpoint can still give its later unrecorded sessions assumed credit on that date. A revision that captured the old remainder and saved after the checkpoint does not.
- Tomorrow's saved plan still displays its own sessions after today's credited work would already have finished the task. The projected finish date is today. The following forecast day places nothing for it. The tomorrow column shows `needsRefresh` only when the 1.3.0 rule already would.
- A saved plan schedules B at 09:00, finishes live blocker A at 10:00, and schedules B again at 11:00. The column lists B in `dependenciesIgnored`, gives the 09:00 session no assumed credit, and credits the 11:00 session. The copy does not claim the dependency was added later, and the saved plan is unchanged.
- A task due inside the span whose credited remainder reaches zero on time is `ON_TRACK`. The same shape finishing after the due date is `AT_RISK`. A due date before `currentDate` is `OVERDUE` even when the effort is unknown. Unknown effort with a future due date is `CANNOT_FORECAST`. A due date after the span, with work left, is `BEYOND_HORIZON`. `AT_RISK` caused by a blocker that finishes after the due date still names that blocker. In A blocks B and B blocks C, C's `waitingOn` names B and its `upstreamBlockers` names A when A is the unfinished or unknown cause.
- Every horizon day already has a saved plan, and a newly added due task appears on none of them. That task still has a row, no segments, and a deadline status. Its task-list badge can say "At risk" or "Cannot forecast".
- A task due on Sunday shows that date beside its title. Sunday gets a column marker only when Sunday is a displayed column.
- The horizon request fails. The task list still loads, its actions still work, and it says the deadline forecast is unavailable. It does not present the tasks as on track.
- Monday's credited work leaves B unfinished, and A blocks B. Tuesday's forecast treats B as must-continue and gives A that inherited group before dependency repair.
- A 60-minute bar on a saved four-hour day and a 60-minute bar on an eight-hour forecast day have the same length when eight hours is the longest full window in the span.
- The horizon page is left open. The next minute changes `currentTime` in the query and refetches. Returning to the page refetches as well.
- A progress save commits while the horizon read is loading its inputs. The response uses the state from before that save, or the state from after it, and does not mix the old remainder with the new outcome.
- Today with no plan, requested after the work window has ended, contributes an empty forecast column and places the remainder on the next working day.
- The horizon with no plannable tasks and no saved plans in the span returns **200**, the day columns, and an empty task list, and it does not call the provider.

## Suggested Decomposition

This spec is one milestone. A later implementation plan can split it without changing the product rules:

1. Dependency storage, cycle checks, task API, and task UI.
2. Inherited urgency, prompt labels, repair, `BLOCKED` placement, revision snapshots, captured checkpoint ids, and warning copy.
3. Working weekdays on preferences.
4. The pure horizon forecast, assumed credit, and `GET /api/horizon`.
5. The Gantt page, deadline badges, forecast-failure handling, and cache invalidation.
